# 0012 · Customer self sign-up at Mon-A Bank

- **Status:** accepted · 2026-11-15
- **Issue:** #103 (twin of #95 on `Monolithic`) · **Extends:** [ADR 0008](0008-spring-security.md)

`Monolithic` has an ADR with the same number and title for #95. Both branches behave the same; this one records how the decision fits ports and adapters. ADR 0011 (the `integration` layer) only applies to phase 1, so it is not on this branch.

## Context

Until #103 only the administrator opened accounts on this branch, and users came from configuration (ADR 0008). The IBAN was already generated by the factory (`AccountNumberSequence`, #18) and `TaxId` already existed (#98). The user asked for the same bank-like digital sign-up as on `Monolithic`: a visitor becomes a customer of **Mon-A Bank** from the login page, with immediate opening and no administrator approval. A customer is identified by their document and can hold several accounts.

Constraints:

- The core does not depend on Spring, and `application` does not depend on Spring Security (`el_nucleo_no_depende_de_spring`, `la_aplicacion_no_depende_de_spring_security`), but signing up creates a user with a password.
- The input adapters only know the input ports (`los_adaptadores_de_entrada_solo_conocen_los_puertos_de_entrada`).
- `InMemoryUnitOfWork` gives mutual exclusion but no rollback (#78).

## Decision

- **Public sign-up** on the web (`/login` with two doors, then `/signup` in three steps, CSRF on) and in the API (`POST /api/customers`, no credentials). Immediate opening; the customer ends signed in on the web.
- **Customer aggregate** (`Customer`: document, name, e-mail) and the value object `EmailAddress` in `domain.model`, with the output port `CustomerRepository` (one customer per document, R30, checked atomically by `InMemoryCustomerRepository`).
- **Customer ↔ username as an application output port** (`CustomerOwnershipRepository`, decided by the user on 2026-11-15), like `AccountOwnershipRepository`: the user's identity does not reach the domain. A username belongs to one customer (R30).
- **New input-port operations:** `signUp`, `openAnotherAccount` and `regenerateAccountNumber` in `CheckingAccountCommands`, `isUsernameTaken` in `CheckingAccountQueries`. They run in the unit of work; "all or nothing" comes from the order of the operations (build the account, check document and username, then save), because the unit does not roll back.
- **Users created at runtime in the input adapters:** `adapter.in.CustomerRegistration` (shared by web and REST, like `SecuritySupport`) checks that the username is free (Spring Security users and `isUsernameTaken`), calls `signUp` and then creates the user with role `USER` and a BCrypt hash in the `UserDetailsManager`. The four steps run under one lock. The core never sees credentials.
- **The bank assigns every IBAN** (entity `9999`, branch `0001`); the administrator can only replace one with another generated one (R32), and the repository adapter reindexes the number. The administrator's opening takes the document: an existing customer gets another account; a new one is registered with name, e-mail and username.
- **Document:** DNI or NIE with its control letter checked (`TaxId`, R28), normalised with `Locale.ROOT`.
- **No new domain events** for sign-up or IBAN changes (decided by the user on 2026-11-15): the existing `CheckingAccountOpened` is published for every account the sign-up opens.

## Alternatives

- **Customer ↔ username inside the customer adapter**, as on `Monolithic`: fewer types, but it would put identity in a domain port. Discarded by the user.
- **`CustomerRegistered` and `AccountNumberReassigned` events:** the notification listener could announce them, but nothing consumes them yet. Left out by the user.
- **User management in `application`:** it would need Spring Security in the core or a new port for credentials. Discarded: credentials are an input-adapter concern here.
- **Sign-up pending administrator approval**, **document unique per account** and **persisting users in H2:** discarded for the same reasons as in the `Monolithic` ADR.

## Consequences

- Both branches have customers, generated IBANs and runtime users, with the same routes, messages and demo IBANs.
- `POST /api/accounts` changed incompatibly (conditional customer fields, new `holderEmail`), documented in `openapi.yaml`.
- `CheckingAccountService` gains two output ports (`CustomerRepository`, `CustomerOwnershipRepository`) wired in `config.DomainConfiguration`.
- **Accepted risks** (local practice project): no e-mail verification; no rate limit (closed by #131, [ADR 0018](0018-sign-up-limit.md)); customers, accounts and users live in memory; if creating the user failed for a reason other than a taken username, a customer without a usable login would remain; the wizard keeps the password in the server session between steps 2 and 3 (never rendered).
