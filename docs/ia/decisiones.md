# Project decisions

> Annex of [`estado-del-proyecto.md`](estado-del-proyecto.md). **It is not read at the start of every session**: look it up when the task touches the area of a decision (planning, implementing or reviewing). The background architecture decisions are in the ADRs (`docs/adr/`); the detailed ones that affect the next issues go here.

## Decisions already made that affect what comes next

- **End of phase 1 (#13):** `Monolithic` is frozen at the `v1-monolito` tag, like `master` (only touched by the user's explicit decision). `Hexagonal` is created from `Monolithic` and becomes the repository's default branch: phase 2 PRs go against it.
- **End of phase 2 (#23):** the `v2-hexagonal` tag marks the phase-2 snapshot. Unlike `Monolithic`, `Hexagonal` is **not frozen**: it stays the active and default branch, and the next work (#70 translation, #71 Graphify, #72 web) goes against it, without a milestone. The comparison and its links always use the tag, never the branch. Decided by the user on 2026-11-04.
- **Base package `com.dawnrock.ddd` (2026-11-23, user's decision):** the Java packages, the Maven `groupId` (`com.dawnrock`), the skill templates and the docs use the repository owner's name. The name inherited from the course's starting point belongs to a third party and must not appear anywhere in the project (code, docs, plans, issues). The rename was applied on `Hexagonal`, `Monolithic` and `master` by the user's explicit authorisation; git history and the `v1-monolito`/`v2-hexagonal` tags are left as they are (no history rewrite), so links and `git diff` commands against the tags avoid the old package path.
- **Documentation in English (#70):** every document in `docs/` is in English except `docs/analysis/` (#52); file names stay in Spanish (renaming would touch `CLAUDE.md`, skills, agents and the CI script). The glossary keeps a Spanish-term column, because error messages and `@DisplayName` use it; strings the code produces (API `title`/`detail`, log lines) stay in Spanish wherever they are quoted. Decided by the user on 2026-11-04.
- **Phase 2 packages (#14, ADR 0006):** `presentation` → `adapter.in` (the shared security support, in its root) and `persistence` → `adapter.out.persistence`. `LayeredArchitectureTests` was adjusted provisionally until #22, which replaced it with `HexagonalArchitectureTests`.
- **Persistence output ports (#15):** `domain.model.CheckingAccountRepository` and `application.AccountOwnershipRepository` (in `application` because of ADR 0008); the in-memory adapters are package-private and nobody outside `adapter.out.persistence` and `config` knows them (ArchUnit rule). Each port has an abstract test contract (`*Contract`) that any implementation inherits. Tests in other packages get the adapters through `PersistenceTestAdapters`, typed as ports. The persistence layer may know `application`, because it implements one of its ports.
- **Input ports (#16):** `application.CheckingAccountCommands` (open, deposit, withdraw, transfer) and `application.CheckingAccountQueries` (list, details); `CheckingAccountService` implements them and the input adapters (and `DomainModelRunner`, formerly `DemoDataLoader`) only know the ports (ArchUnit rule). Decided with the user (2026-11-03): **no query objects** (queries receive the `Caller` and, at most, an id; a type that wraps a single value adds no rules) and **no renaming** of the service to `CheckingAccountApplicationService` as the issue said (nobody outside `application` sees it). A query with filters would get its own Immutables query.
- **Domain events (#17):** the account records `CheckingAccountOpened`, `MoneyDeposited`, `MoneyWithdrawn` and `WithdrawalRejected` (`record`s in `domain.model`) and hands them over with `pullDomainEvents()`; `CheckingAccountService` publishes them through the `DomainEventPublisher` port after saving each account and, since #165, **inside the same unit of work** (outbox, see below). Decided with the user (2026-11-03): opening an account records two events (account opened + deposit of the initial deposit); transfers have no event of their own (withdrawal + deposit); consumers were synchronous until #165. The ArchUnit rules now treat `adapter.out..` as a layer, and its adapters do not know each other.
- **Account factory (#18):** `CheckingAccountFactory` (domain) opens the accounts with the `AccountNumberSequence` and `IncomeVerifier` ports; `CheckingAccount.open` is package-private and tests create accounts without the factory through `TestAccounts` (bridge `TestCheckingAccounts`). Opening receives the holder's **NIF** (format only, no check letter), not the IBAN or the segment; R20: high net worth only with verified income **above €100,000.00**; an unknown NIF opens as retail. Since #20 the factory is built by `config`. Incompatible change to `POST /api/accounts` without versioning (no external clients). Decided with the user on 2026-11-03. Contract: `docs/contracts/account-factory.md` (expand → contract transition closed in T12).
- **CLI adapter (#19):** the demo data is the `adapter.in.cli.DomainModelRunner` input adapter (`demo` profile), which only uses `CheckingAccountCommands` and acts as `CallerDef.system()` (administrator). At the user's request (2026-11-03), besides opening the three accounts it deposits €200 into Ada's, withdraws €50 (approved) and €1000 (rejected) from Alan's and transfers €300 from Grace to Ada by her generated IBAN: final balances Ada 1500, Grace 4700, Alan 200. Each operation leaves a `[demo]` trace.
- **Core built in `config` (#20):** `config.DomainConfiguration` declares the `@Bean`s of `MoneyTransferService`, `CheckingAccountFactory`, `CheckingAccountService` and the two event consumers; the domain and `application` carry no Spring annotations (rule `el_nucleo_no_depende_de_spring`). Decided with the user (2026-11-04): the consumers keep `@EventListener` (the only exception, in `application.listener`), and the output adapters keep registering themselves (package-private, outside the core); `config` receives them by their port.
- **Adapter tests (#21):** each adapter is tested without the hexagon (table in `fase-2-hexagonal.md`); no input-adapter test starts the full context, guarded by `AdapterTestIsolationTests` (ArchUnit over the tests). Each persistence port has its `*Contract`. Only the missing tests are added: the review found the 400 for the currency of REST withdrawals uncovered; every other 404/422/400 path was already covered (decided with the user, 2026-11-04).
- **Hexagonal rules (#22):** `HexagonalArchitectureTests` replaces `LayeredArchitectureTests`: `onionArchitecture()` (model, domain services, application and one adapter per technology) plus explicit rules for ports, Spring and security; the security support in the root of `adapter.in` and `config` stay outside the rings. `la_persistencia_no_tiene_interfaces` (phase 1) is dropped. Our own packages are named with their full prefix (`com.dawnrock.ddd.config..`), because `..config..` also matches Spring packages.
- **Input ports and services per use case (#174, user's decision of 2026-11-25):** `CheckingAccountCommands` became `AccountOpeningCommands` (open, sign up, another account, regenerate an IBAN), plus `MoneyMovementCommands` (deposit, withdraw, transfer) and `SegmentReviewCommands` (scheduled review); `CheckingAccountQueries` stays. One public service per port (`AccountOpeningService`, `MoneyMovementService`, `AccountSegmentReviewService`, `CheckingAccountQueryService`), each built in `config` from the output ports; the shared mechanics are package-private collaborators of `application` (`AccountUnitOfWork`, `AccountAccess`, `AccountOpener`, `CustomerDirectory`, `UsernameAvailability`, `DueSegmentReview`, `AccountViews`). A new use case goes into the port of its group, or a new port; ArchUnit forbids anyone but `application` and `config` to depend on a class that implements an input port. The #16, #19 and #20 entries below describe the single service before #174. Application tests build the services with `support.ApplicationServicesFixture`.
- **Customer sign-up on `Hexagonal` (#103, ADR 0012):** same behaviour as #95 on `Monolithic` (routes, messages, demo IBANs). Decided by the user on 2026-11-15: the customer ↔ username relation is the application output port `CustomerOwnershipRepository` (not inside the customer adapter as on `Monolithic`), and there are **no new domain events** for sign-up or IBAN changes. Rules R28-R32 here are R27-R31 there. The unit of work does not roll back, so `signUp` and the administrator's opening are all or nothing by the order of their operations (build the account, check document and username, then save). `CustomerRegistration` lives in the root of `adapter.in` and only uses the input ports; `SecuritySupport` exposes a `UserDetailsManager`. Teammates of `/implement-plan-team` were launched with `isolation: worktree`: those worktrees start from `master`, so the lead authorised `git switch -C <branch> <contract commit>` on the empty branch.
- **Automatic merge with green checks (2026-11-17):** decided by the user. When the user asks for a PR, Claude merges it like the GitHub **Merge pull request** button with its default option (*Create a merge commit*), pinning the head SHA, once every check of the head commit is green, the automated review leaves no blocking finding and there is no conflict; never against `master`. A failing check is fixed on the same branch, never skipped. PRs Claude opens on its own still need the user's "yes". Rule in step 7 bis of `implement-plan`, also used by `implement-plan-team`.
- **Only the five most recent plans in `docs/plans/` (2026-11-17):** decided by the user. `plan-feature` removes the older ones with `git rm` in the commit of the new plan; they stay in the git history and as a comment on their issue. Links to removed plans point to their issue instead.
- **Phase 2 issues updated (2026-10-30):** #15 adds a port in `application` for account ownership (`InMemoryAccountOwnershipRepository`); #18 changes the opening contract (generated IBAN, segment decided by the factory) and becomes a team issue (back + web).

- **Web ↔ back contract** (ADR 0007, approach A): service, commands and views of `application`, plus an OpenAPI fragment. The web does not consume the REST API.
- **REST DTOs:** they may be Immutables types with `@JsonSerialize`/`@JsonDeserialize` from `tools.jackson.databind.annotation` (ADR 0003).
- **Errors:** `DomainException` → 422, `NotFoundException` → 404, `IllegalArgumentException` and validation → 400 (`RestExceptionHandler`). `AccountNotFoundException` (#5) extends `NotFoundException`.
- **Unique account number (R16):** the opening use cases check it (`AccountOpener` since #174, `CheckingAccountService.openAccount` before) with `findByAccountNumber` and throws `DuplicateAccountNumberException` (422). The repository's `IllegalStateException` is left only for the race between two simultaneous openings (500, accepted limitation).
- **Commands validate before calling the domain.** The 400 for `IllegalArgumentException` is only a safety net.
- **Shared validation:** the REST request (`record` with Bean Validation) and the web form apply the same constraints (#5 contract), and the web sends the command's rejection back to the form instead of a 500.
- **Cookie-only web session** (`server.servlet.session.tracking-modes=cookie`): with URL tracking, the redirect after a Post/Redirect/Get went to `/;jsessionid=…` and Spring answered 404.
- **Segments and other domain enumerations** travel as `String` in commands and views (D4); a test checks that `OpenAccountCommandDef.SEGMENTS` matches `CustomerSegment`.
- **Rejected withdrawal:** it is not an error. The service returns the transaction with `REJECTED` (REST 201) and the web shows it as a notice, with a text valid for both segments.
- **Non-positive amount = 400 / field error** (R3), not a domain error; the command also rejects an amount that rounds to zero in its currency (`0.001` EUR). Decided by the user on 2026-10-23 when planning #6.
- **404 on the web:** `@ControllerAdvice` scoped with `basePackageClasses` to `presentation.web`. Do not scope it by `@Controller`: `@RestController` carries it too and would catch the API's errors.
- **Transfers (#7):** they live in the `MoneyTransferService` domain service (plain Java, stateless), which since #20 is built by `config.DomainConfiguration` and passed to `CheckingAccountService` through its constructor. Order: same account (R17, 422) → target currency (R19, 422) → withdrawal on the source → deposit on the target only if approved (R18). A rejected transfer is 201 with `REJECTED`, like a withdrawal. Recorded as `WITHDRAWAL` + `DEPOSIT`, with no types of its own. Target account not found = 404. `POST /api/transfers` in its own `TransferController`.
- **Domain without Lombok (ADR 0009, 2026-10-26):** supersedes the domain part of ADR 0003. `@Getter` in `domain..` broke D1 because of `@lombok.Generated`; now `check-domain.mjs` rejects any `import lombok`/`@lombok.` there and the entity template writes accessors and `equals`/`hashCode` by id by hand.
- **Login and roles (#50, ADR 0008):** Spring Security authenticates (form and session on the web, HTTP Basic without a session on `/api`, replaced by JWT Bearer tokens in #122) and checks roles on the URLs; account ownership is checked by `CheckingAccountService` with the `Caller`. Someone else's account = 404; missing role = 403. The owner is a user name stored in `persistence`, never in the domain. Transfers go to a typed IBAN (`targetAccountNumber`, incompatible API change). Demo users with a BCrypt hash; real administrator through environment variables.
- **Graphify only for dependencies (#57, ADR 0010):** the code graph (`graphify-out/`, not versioned, one per worktree) is queried with `node scripts/graphify.mjs affected|path` to know who depends on a class; Grep is still used for everything else. No hook: its reminders cost more than they saved. `implement-plan` regenerates the graph when it creates the worktree (`node scripts/graphify.mjs update .`).
- **Status in the views (#82):** `TransactionSummary` and `TransferSummary` expose `approved()` / `rejected()` (default methods, not Immutables attributes, so builders and JSON do not change); the adapters never compare status strings. REST keeps the `status` string. `CheckingAccount.tryWithdraw` evaluates whether the withdrawal is allowed before recording the transaction.
- **Deploy on Render (#85):** each branch is a separate web service on Render's free plan, built from the repository's `Dockerfile` (Render runs Java only through Docker); the application code does not change. The image sets the `demo` profile, the port from `PORT`, `-XX:MaxRAMPercentage=75` for the 512 MB instance and turns the H2 console off. On a public URL the `demo` password is replaced through `APP_SECURITY_USERS_<n>_USERNAME` / `_PASSWORDHASH` / `_ROLE` (all three per user: Spring Boot replaces the whole list when a variable sets part of it; the user names stay because the demo accounts belong to them). Two services created by hand, not a `render.yaml` blueprint. Decided with the user on 2026-11-11; guide `docs/deploy/render.md`.
- **Web footer without the project name (#91):** the footer only says the phase and its architecture: `Fase 2 · arquitectura hexagonal` on `Hexagonal`, `Fase 1 · arquitectura monolítica` on `Monolithic`. The `Monolithic` change is a second exception to its freeze, this time in `src/` (template and web test), approved by the user on 2026-11-12; `v1-monolito` does not move.
- **PRs against `Monolithic` do not close their issue (#86):** GitHub only applies `Closes #n` when merging into the default branch (`Hexagonal`), so the issue is closed by hand after the merge, with a comment pointing at the PR. The `Hexagonal` status catches up in its next PR. Found on 2026-11-12.
- **Claude Code configuration (#79):** `buscador-referencias` goes straight to Grep for questions about methods or fields (measured: −17 % on the method question, dependency questions unchanged; ADR 0010); `implement-plan-team` records that the lead merges the teammates' contract reviews and creates their worktrees from the contract commit; `CLAUDE.md` mentions the `demo` profile and rule D4. Approved by the user on 2026-11-11.
- **Unit of work (#78):** every use case of `CheckingAccountService`, queries included, runs inside the `application.UnitOfWork` port (`<T> T execute(Supplier<T>)`); the in-memory adapter `InMemoryUnitOfWork` serialises them with one fair lock (enough for a practice repository that hands the same account object to everyone; a database would lock only the rows involved). Domain events are collected when each account is saved and published once the unit has finished, one batch per account; nothing is published if the unit fails. The adapter cannot roll back changes already made to aggregates; if a unit failed after changing an account and before saving it, that account would keep its unpublished events and the next use case that saves it would publish them (no use case can fail there today). Decided with the user on 2026-11-05 (not optimistic locking, not only an atomic `saveAll`).
- **Review leftovers (#77):** the holder-name rule is now R21 with its tests; the account itself rejects its own number as counterpart (`SameAccountTransferException`, R17), besides the check in `MoneyTransferService`; the segment label of the input adapters lives in `adapter.in.SegmentLabels` (root of `adapter.in`, next to the security support), used by the web and the CLI. Decided with the user on 2026-11-05.
- **Transfers show their counterpart (#72):** each transaction of a transfer records the other account (`Transaction.counterpart()`, optional `AccountNumber`), set only through `CheckingAccount.tryWithdrawForTransfer` / `depositFromTransfer`; transfers stay `WITHDRAWAL` + `DEPOSIT` (#7). `TransactionSummary.counterpartAccountNumber` (`Optional`) and the REST `counterpartAccountNumber` (omitted when absent: `@Nullable` + `NON_NULL`, because Jackson 3 writes an empty `Optional` as `null`). The web lists transactions newest first by reversing a copy of the list (instants can be equal); `application` and REST keep chronological order. The segment label lives only in `WebFormat.segment` (since #77, in `adapter.in.SegmentLabels`). Decided with the user on 2026-11-05; contract `docs/contracts/transfer-counterpart.md`.
- **Graphify confirmed on phase 2 (#71, ADR 0010):** measured again with `scripts/measure-graphify.mjs` (5 questions × 2 runs × 3 configurations, Haiku): the current rule saves 32 % on dependency questions, and using the graph first for every search does not pay off. The use is not widened. Headless measurement sessions need `--allowedTools` for the Graphify commands, because an untrusted workspace ignores the project's `permissions.allow`.
- **Split status (#57):** `estado-del-proyecto.md` is kept short (it is read in every session); decisions, pending items and history go to their annexes.
- **Customer segment (#98, twin of #94):** nobody chooses it. At opening the factory decides it from the verified income (R20); afterwards the account balance counts: €100,000.00 promotes at once, and a high-net-worth account that falls below it is reviewed one month later (`CheckingAccount.nextSegmentReview`). The review is the domain service `SegmentReviewService`, which asks `IncomeVerifier` again: with a high income the holder keeps the segment and is reviewed every six months; otherwise goes back to retail. The domain never asks for the time: the application passes a `Clock` instant, before every debit and from the daily `adapter.in.scheduler`. The tax agency is never asked on a promotion. Rule numbers differ between branches (here R22-R27; on `Monolithic`, R20-R23 until #99). Generated IBANs: entity `9999`, branch `0001` (Mon-A Bank, invented).
- **OpenAPI contract vs. implementation (#108):** amounts (movements, transfers and initial deposits) go from 0.005 (rounded half-up to 0.01) to a **technical** maximum of 999,999,999.99 per operation, checked in `application.CommandValidation` (shared by REST, web and CLI) and with `@DecimalMin`/`@DecimalMax` in the REST DTOs; it is not a business rule, so not in the glossary. Request `currency` is `enum: [EUR, null]` in the contract (every account is in EUR); optional strings that the API takes as absent when `null` are `type: [string, 'null']`. The public `POST /api/customers` answers 401 when wrong HTTP Basic credentials are sent (documented, not changed; since #122, when an invalid Bearer token is sent). `SecuritySupport` declares a `StrictHttpFirewall` that also allows `QUERY`, so an undeclared `QUERY` answers 405 with `Allow` like `PUT`/`DELETE` (Spring answers those 405s without a `ProblemDetail` body). No `multipleOf: 0.01` in the contract: validators compute it with floats. Decided with the user on 2026-11-17.
- **No multipart (#113):** `spring.servlet.multipart.enabled=false`. Nothing accepts uploads, and with it on Spring parsed any `multipart/form-data` body before choosing a handler, so a request without a boundary failed with an untranslated 500. A feature that needs uploads must turn it back on and translate `MultipartException`. Decided with the user on 2026-11-17.
- **Contract tests (#107, ADR 0013):** black-box contract tests at hexagon level with Schemathesis 4.33.4 (`scripts/contract-test.mjs`, config in `schemathesis.toml`), in the CI after `./mvnw verify`, locally from `CLAUDE.md` and in `implement-plan`'s global criteria when a plan touches the API. Deterministic generation (no seed is used in that mode). Legitimate rejections of schema-valid data are **declared, never disabled**, per operation: `422` on the operations with business rules (`deposit`, `withdraw`, `transfer`, `openAccount`, `signUp`) and `400` on `openAccount` and `signUp` (DNI/NIE control letter, #103 rule; accepted blind spot for other 400s there, covered by the REST adapter tests). A new kind of legitimate rejection is a reviewed change of `schemathesis.toml`; anything else Schemathesis reports is a contract discrepancy. Decided with the user on 2026-11-17.
- **OpenAPI style guide (#109):** `docs/api/style-guide.md` lists the contract conventions; the checkable ones are rules in `redocly.yaml` (built-in rules raised to `error` plus `rule/*` assertions: camelCase `operationId`, one tag, required request bodies, 4XX as `application/problem+json`, `info.contact`, no `example` inside schemas), run by the existing CI Redocly step. `info.contact` names the project and its GitHub issues, never a personal e-mail. Decided on 2026-11-17 (within `/advance-issues`).
- **Contract examples and 415 (#110):** every success response has examples, with named ones for the interesting cases (empty list, retail/high net worth, rejected withdrawal and transfer, the four usual 422s); they are based on real responses of the `demo` profile (a few ids and IBANs of the opening and approved-withdrawal examples are illustrative, with valid IBANs), and `no-invalid-media-type-examples` is an error, so an example that does not match its schema fails the lint. The 415 answers in Spanish ("Tipo de contenido no admitido") through `RestExceptionHandler` and is documented on the operations with a body. `servers` lists the Render deployment of `Hexagonal` (`https://proyect-ddd-claude.onrender.com`; `Monolithic` is at `https://mon-e-bank-monolithic.onrender.com`). Decided on 2026-11-17 (within `/advance-issues`; the URLs given by the user).
- **Swagger UI (#111):** option A, chosen by the user: a static page at `/api-docs` (`adapter.in.web.ApiDocsController` + `static/api-docs/index.html`) loading `swagger-ui-dist` 5.34.1 from jsDelivr with SRI hashes, over the hand-written contract that the build copies into the jar as `/openapi.yaml` (`pom.xml` resources, no dependency; the `Dockerfile` and `.dockerignore` bring `docs/api/openapi.yaml` too). Both paths are public; the API used HTTP Basic then (Bearer since #122). The contract's first server is relative (`/`), so "Try it out" targets the server that serves the page. Upgrading Swagger UI means new SRI hashes, computed from the npm package. Decided on 2026-11-17.
- **Contract versioning (#112, ADR 0014):** `info.version` follows SemVer from `1.0.0`: major when `oasdiff breaking` reports an `ERR`, minor for a compatible addition, patch for documentation; every contract change bumps it and adds an entry to `docs/api/CHANGELOG.md` (no more "incompatible change" notes in descriptions). `scripts/check-contract-version.mjs` enforces it on every PR (oasdiff `v1.35.0` via `go install`), and `plan-feature` asks for it in the API task (approved by the user). Decided on 2026-11-17.
- **JWT Bearer on the API (#122, ADR 0015):** `/api/**` only accepts `Authorization: Bearer` with an HS256 JWT from the public `POST /api/auth/token` (`iss=ddd-lab`, `sub`, `roles`, 15 min); HTTP Basic is gone and the contract is 2.0.0. The secret is `APP_JWT_SECRET` (at least 32 bytes; the `demo` profile has a development one; without it, a random key per start). `AccessTokenIssuer` builds its own `ProviderManager` so the web login keeps its manager. The two public API paths are public for any method, so an undeclared method answers 405, not 401. Schemathesis gets the token with `[auth.dynamic.openapi.bearerAuth]`. The web keeps form login and session. `APP_JWT_SECRET` is set on the Render `Hexagonal` service (the user, 2026-11-18). Decided with the user on 2026-11-18.
- **Web frontend libraries (#124, ADR 0016):** Bootstrap 5.3.8 (dark theme, every screen on plain Bootstrap; the custom theme of #48 is gone), htmx 2.0.11 (loaded, used from #125), Alpine.js 3.17.5, Lucide (`lucide-static` 1.67.0, SVG sprite through `fragments/icons :: icon(name)`) as WebJars with `webjars-locator-lite`, and Motion 14.14.0 copied into `static/vendor/motion` (no WebJar). Progressive enhancement: everything works without JavaScript; the account actions stay `<details>` and Alpine.js only adds the accordion. Static resources are cached for a year with the WebJar version or a content hash in the URL (`spring.web.resources.chain.strategy.content`), because Spring Security's `no-store` made every page download them again; pages stay `no-store`. `@view-transition` only applies with scripting enabled and no reduced motion (without JavaScript Chromium sometimes ignored clicks after navigating). Tests that compared literal markup check text and icons instead. Decided with the user on 2026-11-18.
- **htmx on the account detail (#125, ADR 0016):** the pattern #126 reuses. Each operation takes `@RequestHeader(name = "HX-Request", defaultValue = "false") boolean htmx`; `AccountWebController.notice(...)` either adds the notice to the model, removes the submitted forms and their `BindingResult` (otherwise Thymeleaf repaints the typed values) and returns the `panel` fragment, or adds a flash attribute and redirects. Errors render the same fragment. The fragment wraps notices, balance, actions and transactions in `#account-panel` (`hx-target` + `hx-swap="outerHTML transition:true"` inherited by the forms); no `hx-boost` and no history changes. Security: `HtmxLoginRedirect` is the web chain's entry point and access-denied handler; for htmx it answers 401 + `HX-Redirect: /login` when there is no authentication or the CSRF token is missing (an expired session loses it), and the 403 page for an invalid token. Decided on 2026-11-18.
- **htmx navigation for the rest of the web (#126, ADR 0016):** hybrid approach chosen by the user on 2026-11-20: `hx-boost` on every full page's `<body>` (`hx-swap="innerHTML transition:true"`) and fragments only where an interaction needs them. Rules for new screens: a full page needs nothing (`HtmxBoostTemplatesTests` fails if a page lacks the boost); a link inside a fragment with its own `hx-target` (like "Abrir otra cuenta" in `#account-panel`) needs `hx-target="body"` and its own `hx-swap`; a page with its own script must put it in `app.js` or opt out with `hx-boost="false"`. Validation stays on submit (errors appear without reloading); per-field validation on blur is a later option. The history cache is off so that no balance or IBAN stays in `sessionStorage`. Any error answer that is an HTML page (403, 404, or Spring's for the rest) replaces the body, as a normal navigation would.
- **Limit on login attempts (#130, ADR 0017):**
  - **Policy (OWASP), chosen by the user on 2026-11-20:** 3 failures per user + IP and 10 per IP block for 30 minutes, even with the right password (`app.security.login-attempts.*`).
  - **Where:** `ThrottledAuthenticationProvider` and `LoginAttempts` in the root of `adapter.in`, created by `SecuritySupport` as beans, so the `@WebMvcTest`s that import it get them; they use the core's `Clock` when there is one. The web form login and `AccessTokenIssuer` use the same provider and pass the IP in `WebAuthenticationDetails`.
  - **Answers:** the web redirects to `/login?blocked`; the API answers 429 `ProblemDetail` with `Retry-After` (contract 2.1.0). An unknown user gets the same treatment as a known one.
  - **IP:** from `ClientIpResolver` since #133 (see below); `native` alone counted Cloudflare's IP.
  - **Contract tests:** `contract-test.mjs` raises the thresholds.
  - **Tests that fail logins on purpose** use their own IP (`setRemoteAddr`, or `X-Forwarded-For` against the real server), so they do not lock other tests sharing the same context.
  - **Sign-up limit:** split into #131.
- **Client IP behind Render and Cloudflare (#133, ADR 0017):** Render serves through Cloudflare, so `forward-headers-strategy=native` alone counted Cloudflare's edge.
  - **`ClientIpResolver`:** the IP comes from it, in the shared security support, through `ClientIpAuthenticationDetailsSource`, which the web login and `TokenController` use.
  - **Trusted proxies:** `app.security.trusted-proxies` holds the internal ranges and Cloudflare's official ranges; `scripts/check-cloudflare-ips.mjs` keeps them in sync.
  - **Reuse:** #131 and any future per-IP limit must take the IP from the resolver, never from `getRemoteAddr()`.
- **Sign-up limit (#131, ADR 0018, agreed with the user on 2026-11-23):** 3 successful sign-ups per client IP and 50 in total per sliding hour (`app.security.sign-ups.*`); failed sign-ups give their slot back. `SignUpLimit` lives in `adapter.in` and `CustomerRegistration.register(command, password, clientIp)` reserves the slot; API 429 `TooManySignUps` with `Retry-After`, web message from step 1 (read-only check) and at the last step. Tests that make many sign-ups from one IP (full context, contract tests) raise the limits. **Probing limit (#139, agreed on 2026-11-23):** sign-ups failing with `UsernameTakenException` or `DuplicateCustomerException` count in a third per-IP window (`max-failures-per-ip`, 10 per hour) that also locks `lockedFor`/`tryReserve`; other failures do not count.

- **Imposed branch in cloud sessions (#136, authorised by the user on 2026-11-23):** when the environment imposes a development branch (`claude/*`) and only allows pushing to it, `implement-plan` (step 2 bis), `implement-plan-team` and `advance-issues` work on that branch without an integration worktree and open the PR from it against the phase branch (never `master`); after the merge the branch is reset to the updated base. TDD, one commit per task, `revisor-ddd` and merging with green checks do not change. Locally, `feat/<slug>` with its worktree stays.
- **Password asked twice in the sign-up (#147):** the web sign-up keeps `password` + `passwordRepetition` on step 2, although the `autofill-sign-up-form` guide advises asking once; each field has its show-password button since #146. Decided by the user on 2026-11-23; #147 closed as not planned.
- **Username lower-cased on the web only (#152):** the web forms (`SignUpForm.setUsername`, `OpenAccountForm.setOwnerUsername`) strip and lower-case the username before validating, so `Margaret` signs up as `margaret`; the API keeps requiring the exact `[a-z0-9._-]{3,30}` format, so web and REST validation differ on purpose in this field. Signing in was case-insensitive then (`InMemoryUserDetailsManager`); since #150 the JDBC store is not, which #157 fixes in the login. All username errors share `OpenAccountCommandDef.USERNAME_MESSAGE`/`OWNER_USERNAME_MESSAGE`, which name every accepted character. Decided by the user on 2026-11-23.
- **Case-insensitive login (#157):** `ThrottledAuthenticationProvider` normalises the typed username with `Usernames.normalize` (strip + lower case `Locale.ROOT`) before the attempt limit and the lookup, so `Elber` signs in as `elber` on the web and through `POST /api/auth/token` (PostgreSQL and H2 compare usernames case-sensitively). `LoginAttempts` and the web forms use the same helper. Stored usernames are always lower case (pattern `[a-z0-9._-]{3,30}`), so no data migration; the API sign-up stays strict (#152). Tests of the login on the real store live in `CaseInsensitiveLoginTests` and `DddLabApplicationTests`, because the `@WebMvcTest`s use the in-memory `TestUsers`, which ignores case. Decided on 2026-11-24.
- **Scripts and line endings (#159):** the `scripts/*.mjs` that parse text accept LF and CRLF (split with `\r?\n` or normalise to LF after reading), since the user works on Windows with `core.autocrlf=true`; no `.gitattributes` rule for that. Script tests use Node's built-in runner (`scripts/*.test.mjs`, no dependency) and the CI runs them (`node --test "scripts/*.test.mjs"`). Decided by Claude under `/advance-issues` on 2026-11-24.
- **Real persistence (#150, ADR 0019):** decided by the user on 2026-11-23. PostgreSQL managed by Neon in production (free plan, AWS `eu-central-1`, next to Render in Frankfurt; `prod` profile with `SPRING_DATASOURCE_*` and no defaults), H2 in PostgreSQL mode locally and in tests (one database per Spring test context, `src/test/resources/config/application.properties`), schema with Flyway and `ddl-auto=validate`. **Option C:** the application always runs on JPA; the in-memory adapters are test doubles in `src/test` and pass the same contracts. **Users and customers in the database:** `UserStore` (`adapter.in`) with `JdbcUserDetailsManager`; configured users are created or updated on every start, signed-up users are kept; the `@WebMvcTest`s import `TestUsers` (in memory). Aggregates are rebuilt with `reconstitute(...)` (coherent state, no events), only from `adapter.out.persistence` (ArchUnit). The unit of work is now a transaction inside the fair lock of #78 (confirmed by the user: no row locks), so a failed use case is rolled back. The demo loader skips loading when accounts exist. JPA adapter tests use `JpaTestDatabase` instead of `@DataJpaTest`, because the contracts' `@Nested` classes get the context of their declaring class.
- **Connection timeouts in `prod` (#156):** driver properties, not URL parameters (`spring.datasource.hikari.data-source-properties.*`): `connectTimeout=15`, `loginTimeout=30`, `socketTimeout=120` seconds, the values checked on Render on 2026-11-23 (pgjdbc lets a URL parameter win over them). Hikari's defaults made explicit: `connection-timeout=30000`, `initialization-fail-timeout=1` (one attempt at start; a failed start keeps Render's previous version) and `keepalive-time=120000` (below Neon's 5-minute suspension; it does not keep Neon awake longer than Render, whose JVM stops when it sleeps). Decided by Claude under `/advance-issues` on 2026-11-24.
- **Test names in English (#166, 2026-11-24, user's decision following the Clean Code course):** test methods are named in English camelCase after the behaviour they check, and `@DisplayName` keeps the Spanish sentence (what the IDE and the reports show). ArchUnit rules are `@ArchTest static void …(JavaClasses classes)` methods, not `ArchRule` fields. `src/test/CLAUDE.md`, the `ddd-building-block` test template and the `plan-feature` template say so. The glossary cites tests as `Class#method` with the English names. To compare test counts, count the `<testcase>` elements of the surefire reports: their `tests` attribute merges cases that share a name across the `@Nested` classes of a file.
- **No magic numbers in production code (#167, Clean Code course):** fixed rules of an algorithm or a format are named `static final` constants in the class that uses them (`TaxId.CONTROL_LETTER_POSITION`, `AccountNumber.BBAN_OFFSET`, `MonABankIbans.IBAN_MODULUS`…); values that change per deployment go to configuration (`*Properties`). When the table itself gives the number, use it (`% CONTROL_LETTERS.length()`). Waiting times shown to people (lockout minutes, `Retry-After`) are rounded up with `adapter.in.Durations`, never by hand. Magic numbers in tests are test data and stay as literals.
- **Static analysis in `./mvnw verify` (#168, ADR 0020):** Checkstyle (course naming rules and `MagicNumber`, not in `src/test`), PMD (four design rules) and CPD, and SpotBugs fail the build. Only hand-written code is analysed (`target/generated-sources` is left out). Existing PMD smells are in `pmd-baseline.properties`; a false positive gets a narrow, commented exclusion (`spotbugs-exclude.xml`, `checkstyle-suppressions.xml`), never a whole package. New code, including #165's, must pass with no new baseline entry.
- **Domain event outbox (#165, ADR 0021, options chosen by the user):** events are stored in `domain_event_outbox` in the transaction of their aggregate (`OutboxDomainEventPublisher`, which refuses to publish outside a transaction) and delivered by the scheduled `OutboxRelay` (every 2 s, at least once, 5 attempts, failed rows kept, published rows deleted after 7 days). Logical type names in `DomainEventTypes`: a new `DomainEvent` must be registered there (a test checks it). Consumers must be idempotent: an event is delivered again after a crash between delivery and marking, and also after one consumer fails when another already received it. Delivery and the record of a failed attempt run in separate transactions, so a consumer that marks the delivery transaction rollback-only still counts an attempt and does not block the queue. Only `adapter.out.event` uses Spring's `ApplicationEventPublisher` (ArchUnit). Full-context tests that need the relay idle use `app.events.outbox.relay-interval=1h` and call `relayPending()`.
- **Neon tools for `backend-dev` (2026-11-23):** decided by the user. Only in this project's agent (`.claude/agents/backend-dev.md`) and **read-only**: describe the project and branches, list databases, roles and operations, tables and table schemas, logs and slow queries. No `run_sql`, branch or role changes: the schema only changes through Flyway migrations in the repository. The Neon plugin brings MCP tools, not skills.
