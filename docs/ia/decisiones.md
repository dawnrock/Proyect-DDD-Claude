# Project decisions

> Annex of [`estado-del-proyecto.md`](estado-del-proyecto.md). **It is not read at the start of every session**: look it up when the task touches the area of a decision (planning, implementing or reviewing). The background architecture decisions are in the ADRs (`docs/adr/`); the detailed ones that affect the next issues go here.

## Decisions already made that affect what comes next

- **End of phase 1 (#13):** `Monolithic` is frozen at the `v1-monolito` tag, like `master` (only touched by the user's explicit decision). `Hexagonal` is created from `Monolithic` and becomes the repository's default branch: phase 2 PRs go against it.
- **End of phase 2 (#23):** the `v2-hexagonal` tag marks the phase-2 snapshot. Unlike `Monolithic`, `Hexagonal` is **not frozen**: it stays the active and default branch, and the next work (#70 translation, #71 Graphify, #72 web) goes against it, without a milestone. The comparison and its links always use the tag, never the branch. Decided by the user on 2026-11-04.
- **Documentation in English (#70):** every document in `docs/` is in English except `docs/analysis/` (#52) and the five phase-1 plans of 2026-10-23, kept in Spanish as a record; file names stay in Spanish (renaming would touch `CLAUDE.md`, skills, agents and the CI script). The glossary keeps a Spanish-term column, because error messages and `@DisplayName` use it; strings the code produces (API `title`/`detail`, log lines) stay in Spanish wherever they are quoted. Decided by the user on 2026-11-04.
- **Phase 2 packages (#14, ADR 0006):** `presentation` → `adapter.in` (the shared security support, in its root) and `persistence` → `adapter.out.persistence`. `LayeredArchitectureTests` was adjusted provisionally until #22, which replaced it with `HexagonalArchitectureTests`.
- **Persistence output ports (#15):** `domain.model.CheckingAccountRepository` and `application.AccountOwnershipRepository` (in `application` because of ADR 0008); the in-memory adapters are package-private and nobody outside `adapter.out.persistence` and `config` knows them (ArchUnit rule). Each port has an abstract test contract (`*Contract`) that any implementation inherits. Tests in other packages get the adapters through `PersistenceTestAdapters`, typed as ports. The persistence layer may know `application`, because it implements one of its ports.
- **Input ports (#16):** `application.CheckingAccountCommands` (open, deposit, withdraw, transfer) and `application.CheckingAccountQueries` (list, details); `CheckingAccountService` implements them and the input adapters (and `DomainModelRunner`, formerly `DemoDataLoader`) only know the ports (ArchUnit rule). Decided with the user (2026-11-03): **no query objects** (queries receive the `Caller` and, at most, an id; a type that wraps a single value adds no rules) and **no renaming** of the service to `CheckingAccountApplicationService` as the issue said (nobody outside `application` sees it). A query with filters would get its own Immutables query.
- **Domain events (#17):** the account records `CheckingAccountOpened`, `MoneyDeposited`, `MoneyWithdrawn` and `WithdrawalRejected` (`record`s in `domain.model`) and hands them over with `pullDomainEvents()`; `CheckingAccountService` publishes them through the `DomainEventPublisher` port **after saving** each account. Decided with the user (2026-11-03): opening an account records two events (account opened + deposit of the initial deposit); transfers have no event of their own (withdrawal + deposit); consumers are synchronous. The ArchUnit rules now treat `adapter.out..` as a layer, and its adapters do not know each other.
- **Account factory (#18):** `CheckingAccountFactory` (domain) opens the accounts with the `AccountNumberSequence` and `IncomeVerifier` ports; `CheckingAccount.open` is package-private and tests create accounts without the factory through `TestAccounts` (bridge `TestCheckingAccounts`). Opening receives the holder's **NIF** (format only, no check letter), not the IBAN or the segment; R20: high net worth only with verified income **above €100,000.00**; an unknown NIF opens as retail. Since #20 the factory is built by `config`. Incompatible change to `POST /api/accounts` without versioning (no external clients). Decided with the user on 2026-11-03. Contract: `docs/contracts/account-factory.md` (expand → contract transition closed in T12).
- **CLI adapter (#19):** the demo data is the `adapter.in.cli.DomainModelRunner` input adapter (`demo` profile), which only uses `CheckingAccountCommands` and acts as `CallerDef.system()` (administrator). At the user's request (2026-11-03), besides opening the three accounts it deposits €200 into Ada's, withdraws €50 (approved) and €1000 (rejected) from Alan's and transfers €300 from Grace to Ada by her generated IBAN: final balances Ada 1500, Grace 4700, Alan 200. Each operation leaves a `[demo]` trace.
- **Core built in `config` (#20):** `config.DomainConfiguration` declares the `@Bean`s of `MoneyTransferService`, `CheckingAccountFactory`, `CheckingAccountService` and the two event consumers; the domain and `application` carry no Spring annotations (rule `el_nucleo_no_depende_de_spring`). Decided with the user (2026-11-04): the consumers keep `@EventListener` (the only exception, in `application.listener`), and the output adapters keep registering themselves (package-private, outside the core); `config` receives them by their port.
- **Adapter tests (#21):** each adapter is tested without the hexagon (table in `fase-2-hexagonal.md`); no input-adapter test starts the full context, guarded by `AdapterTestIsolationTests` (ArchUnit over the tests). Each persistence port has its `*Contract`. Only the missing tests are added: the review found the 400 for the currency of REST withdrawals uncovered; every other 404/422/400 path was already covered (decided with the user, 2026-11-04).
- **Hexagonal rules (#22):** `HexagonalArchitectureTests` replaces `LayeredArchitectureTests`: `onionArchitecture()` (model, domain services, application and one adapter per technology) plus explicit rules for ports, Spring and security; the security support in the root of `adapter.in` and `config` stay outside the rings. `la_persistencia_no_tiene_interfaces` (phase 1) is dropped. Our own packages are named with their full prefix (`com.pronoide.ddd.config..`), because `..config..` also matches Spring packages.
- **Phase 2 issues updated (2026-10-30):** #15 adds a port in `application` for account ownership (`InMemoryAccountOwnershipRepository`); #18 changes the opening contract (generated IBAN, segment decided by the factory) and becomes a team issue (back + web).

- **Web ↔ back contract** (ADR 0007, approach A): service, commands and views of `application`, plus an OpenAPI fragment. The web does not consume the REST API.
- **REST DTOs:** they may be Immutables types with `@JsonSerialize`/`@JsonDeserialize` from `tools.jackson.databind.annotation` (ADR 0003).
- **Errors:** `DomainException` → 422, `NotFoundException` → 404, `IllegalArgumentException` and validation → 400 (`RestExceptionHandler`). `AccountNotFoundException` (#5) extends `NotFoundException`.
- **Unique account number (R16):** `CheckingAccountService.openAccount` checks it with `findByAccountNumber` and throws `DuplicateAccountNumberException` (422). The repository's `IllegalStateException` is left only for the race between two simultaneous openings (500, accepted limitation).
- **Commands validate before calling the domain.** The 400 for `IllegalArgumentException` is only a safety net.
- **Shared validation:** the REST request (`record` with Bean Validation) and the web form apply the same constraints (#5 contract), and the web sends the command's rejection back to the form instead of a 500.
- **Cookie-only web session** (`server.servlet.session.tracking-modes=cookie`): with URL tracking, the redirect after a Post/Redirect/Get went to `/;jsessionid=…` and Spring answered 404.
- **Segments and other domain enumerations** travel as `String` in commands and views (D4); a test checks that `OpenAccountCommandDef.SEGMENTS` matches `CustomerSegment`.
- **Rejected withdrawal:** it is not an error. The service returns the transaction with `REJECTED` (REST 201) and the web shows it as a notice, with a text valid for both segments.
- **Non-positive amount = 400 / field error** (R3), not a domain error; the command also rejects an amount that rounds to zero in its currency (`0.001` EUR). Decided by the user on 2026-10-23 when planning #6.
- **404 on the web:** `@ControllerAdvice` scoped with `basePackageClasses` to `presentation.web`. Do not scope it by `@Controller`: `@RestController` carries it too and would catch the API's errors.
- **Transfers (#7):** they live in the `MoneyTransferService` domain service (plain Java, stateless), which since #20 is built by `config.DomainConfiguration` and passed to `CheckingAccountService` through its constructor. Order: same account (R17, 422) → target currency (R19, 422) → withdrawal on the source → deposit on the target only if approved (R18). A rejected transfer is 201 with `REJECTED`, like a withdrawal. Recorded as `WITHDRAWAL` + `DEPOSIT`, with no types of its own. Target account not found = 404. `POST /api/transfers` in its own `TransferController`.
- **Domain without Lombok (ADR 0009, 2026-10-26):** supersedes the domain part of ADR 0003. `@Getter` in `domain..` broke D1 because of `@lombok.Generated`; now `check-domain.mjs` rejects any `import lombok`/`@lombok.` there and the entity template writes accessors and `equals`/`hashCode` by id by hand.
- **Login and roles (#50, ADR 0008):** Spring Security authenticates (form and session on the web, HTTP Basic without a session on `/api`) and checks roles on the URLs; account ownership is checked by `CheckingAccountService` with the `Caller`. Someone else's account = 404; missing role = 403. The owner is a user name stored in `persistence`, never in the domain. Transfers go to a typed IBAN (`targetAccountNumber`, incompatible API change). Demo users with a BCrypt hash; real administrator through environment variables.
- **Graphify only for dependencies (#57, ADR 0010):** the code graph (`graphify-out/`, not versioned, one per worktree) is queried with `node scripts/graphify.mjs affected|path` to know who depends on a class; Grep is still used for everything else. No hook: its reminders cost more than they saved. `implement-plan` regenerates the graph when it creates the worktree (`node scripts/graphify.mjs update .`).
- **Status in the views (#82):** `TransactionSummary` and `TransferSummary` expose `approved()` / `rejected()` (default methods, not Immutables attributes, so builders and JSON do not change); the adapters never compare status strings. REST keeps the `status` string. `CheckingAccount.tryWithdraw` evaluates whether the withdrawal is allowed before recording the transaction.
- **Deploy on Render (#85):** each branch is a separate web service on Render's free plan, built from the repository's `Dockerfile` (Render runs Java only through Docker); the application code does not change. The image sets the `demo` profile, the port from `PORT`, `-XX:MaxRAMPercentage=75` for the 512 MB instance and turns the H2 console off. On a public URL the `demo` password is replaced through `APP_SECURITY_USERS_<n>_USERNAME` / `_PASSWORDHASH` / `_ROLE` (all three per user: Spring Boot replaces the whole list when a variable sets part of it; the user names stay because the demo accounts belong to them). Two services created by hand, not a `render.yaml` blueprint. Decided with the user on 2026-11-11; guide `docs/deploy/render.md`.
- **Web footer without the project name (#91):** the footer only says the phase and its architecture: `Fase 2 · arquitectura hexagonal` on `Hexagonal`, `Fase 1 · arquitectura monolítica` on `Monolithic`. The `Monolithic` change is a second exception to its freeze, this time in `src/` (template and web test), approved by the user on 2026-11-12; `v1-monolito` does not move.
- **PRs against `Monolithic` do not close their issue (#86):** GitHub only applies `Closes #n` when merging into the default branch (`Hexagonal`), so the issue is closed by hand after the merge, with a comment pointing at the PR. The `Hexagonal` status catches up in its next PR. Found on 2026-11-12.
- **Claude Code configuration (#79):** `buscador-referencias` goes straight to Grep for questions about methods or fields (measured: −17 % on the method question, dependency questions unchanged; ADR 0010); `implement-plan-team` records that the lead merges the teammates' contract reviews and creates their worktrees from the contract commit; `CLAUDE.md` mentions the `demo` profile and rule D4. Approved by the user on 2026-11-11.
- **Unit of work (#78):** every use case of `CheckingAccountService`, queries included, runs inside the `application.UnitOfWork` port (`<T> T execute(Supplier<T>)`); the in-memory adapter `InMemoryUnitOfWork` serialises them with one fair lock (enough for a practice repository that hands the same account object to everyone; a database would lock only the rows involved). Domain events are collected when each account is saved and published once the unit has finished, one batch per account; nothing is published if the unit fails. The adapter cannot roll back changes already made to aggregates; if a unit failed after changing an account and before saving it, that account would keep its unpublished events and the next use case that saves it would publish them (no use case can fail there today). Decided with the user on 2026-11-05 (not optimistic locking, not only an atomic `saveAll`).
- **Review leftovers (#77):** the holder-name rule is now R21 with its tests; the account itself rejects its own number as counterpart (`SameAccountTransferException`, R17), besides the check in `MoneyTransferService`; the segment label of the input adapters lives in `adapter.in.SegmentLabels` (root of `adapter.in`, next to the security support), used by the web and the CLI. Decided with the user on 2026-11-05.
- **Transfers show their counterpart (#72):** each transaction of a transfer records the other account (`Transaction.counterpart()`, optional `AccountNumber`), set only through `CheckingAccount.tryWithdrawForTransfer` / `depositFromTransfer`; transfers stay `WITHDRAWAL` + `DEPOSIT` (#7). `TransactionSummary.counterpartAccountNumber` (`Optional`) and the REST `counterpartAccountNumber` (omitted when absent: `@Nullable` + `NON_NULL`, because Jackson 3 writes an empty `Optional` as `null`). The web lists transactions newest first by reversing a copy of the list (instants can be equal); `application` and REST keep chronological order. The segment label lives only in `WebFormat.segment` (since #77, in `adapter.in.SegmentLabels`). Decided with the user on 2026-11-05; contract `docs/contracts/transfer-counterpart.md`.
- **Graphify confirmed on phase 2 (#71, ADR 0010):** measured again with `scripts/measure-graphify.mjs` (5 questions × 2 runs × 3 configurations, Haiku): the current rule saves 32 % on dependency questions, and using the graph first for every search does not pay off. The use is not widened. Headless measurement sessions need `--allowedTools` for the Graphify commands, because an untrusted workspace ignores the project's `permissions.allow`.
- **Split status (#57):** `estado-del-proyecto.md` is kept short (it is read in every session); decisions, pending items and history go to their annexes.
- **Customer segment (#98, twin of #94):** nobody chooses it. At opening the factory decides it from the verified income (R20); afterwards the account balance counts: €100,000.00 promotes at once, and a high-net-worth account that falls below it is reviewed one month later (`CheckingAccount.nextSegmentReview`). The review is the domain service `SegmentReviewService`, which asks `IncomeVerifier` again: with a high income the holder keeps the segment and is reviewed every six months; otherwise goes back to retail. The domain never asks for the time: the application passes a `Clock` instant, before every debit and from the daily `adapter.in.scheduler`. The tax agency is never asked on a promotion. Rule numbers differ between branches (here R22-R27; on `Monolithic`, R20-R23 until #99). Generated IBANs: entity `9999`, branch `0001` (Mon-A Bank, invented).

## Environment

- Windows 11, Java 21 (Temurin), **Node 24.22.1** with npm 11.19.1, `gh` authenticated as `dawnrock`.
- The repository lives inside OneDrive: if a worktree cannot be deleted because it is locked, delete its folder after `git worktree remove`.
- Repository secrets: `CLAUDE_CODE_OAUTH_TOKEN`, `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. Locally, Telegram is configured in `.claude/settings.local.json`.
- `Monolithic` is protected (PRs only, with `verify` required). `master` is locked.
- If Claude's review fails with `is_error: true` in about 2 seconds, the known cause is a badly copied `CLAUDE_CODE_OAUTH_TOKEN` (401). It is diagnosed with `show_full_output` (see the history of PRs #28-#30).
- Graphify 0.9.97 (`py -m pip install --user graphifyy`, Python 3.14 with the `py` launcher). It is not on the PATH: always use it through `scripts/graphify.mjs`. Without Graphify, everything still works with Grep.
