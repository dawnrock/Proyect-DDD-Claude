# Loose pending items

> Annex of [`estado-del-proyecto.md`](estado-del-proyecto.md). **It is not read at the start of every session**: look it up when planning an issue (there may be notes for it) and when closing a PR (to add or remove pending items).

- Telegram: notices are on since 2026-10-30. If they had to be silenced again, `TELEGRAM_DISABLED=1` (PR #40) in `~/.claude/settings.json`. The failed-CI notice does not depend on that variable (it uses the GitHub secrets).
- **Synchronous event consumers (#17):** `AuditLogListener` and `CustomerNotificationListener` run in the use case's thread: if one failed, the error would reach the user with the account already saved. Accepted while they only write to the log. When a listener that does something real is needed (email, Telegram…), make it asynchronous (`@Async` or `@TransactionalEventListener` with real persistence) so it does not affect the use case. Also, `pullDomainEvents()` empties the list before publishing: if a listener fails, the remaining events are lost (in a transfer, the target's too). A real listener will need an outbox or `@TransactionalEventListener` (#17 review).
- **Login (#50):** the H2 console (`/h2-console`) is for administrators only (same-origin frames, no CSRF on its forms) and the public `/actuator/health` only gives the status; a user can find out whether an IBAN exists by trying a transfer (risk accepted in ADR 0008); there is no limit on login attempts. No password change or user deletion; since #103 customers can sign up (runtime users in memory, ADR 0012). An account can be assigned to a user that does not exist yet. On the public Render deployment (#85) the H2 console is off, but the lack of a limit on login attempts matters more: the password must be strong.
- **Segment review (#98):** `Transaction.occurredOn` uses `Instant.now()` while the review uses the `Clock` bean, so tests move the clock forward instead of dating the movements and there is no end-of-month test; the review dates live in memory and are lost on restart; in a transfer only the source account is reviewed; the account detail does not show the date of the next review.
- **Tax agency failures (#98 review):** an exception from `IncomeVerifier` during a segment review aborts the withdrawal or transfer that triggered it, and stops the daily `reviewSegments` for the remaining accounts. The fake agency never fails; decide the behaviour when a real adapter exists.
- **Customer sign-up (#103):** Accepted risks of ADR 0012: no e-mail verification or rate limit, everything in memory, a failed user creation after `signUp` would leave a customer without login. `isUsernameTaken` and the existing-customer checks of the admin opening are not atomic with the save beyond the global lock of `InMemoryUnitOfWork`; a real persistence adapter needs unique constraints on document and username. Review of #103: a customer saved without a username (only after a partial failure, which the order of operations avoids) cannot get another account (400) nor sign up again (`DuplicateCustomerException`); the administrator can give a new customer a username that already exists as a Spring Security user (the core does not know them); `CustomerOwnershipRepository.assign` replaces the username of a customer (documented, unused by the use cases).
- **Contract tests (#107, ADR 0013):** Schemathesis runs in the CI with deterministic generation; it still warns that `POST /api/transfers` mostly gets 404 (it invents account ids) and that `signUp` rejects most generated documents (random DNIs rarely have a valid control letter): better test data (demo account ids in `schemathesis.toml`, or an example of a valid document) would let it reach more logic. Adapter-level validation in the `@WebMvcTest`s (`swagger-request-validator`) stays an optional later step with its own ADR. On the web chain an undeclared `QUERY` gets 403 (CSRF), not 405.
- **JWT on the API (#122, ADR 0015):** no revocation or deny list (a stolen token is valid until it expires, 15 min; changing `APP_JWT_SECRET` invalidates all of them), no refresh token, and `POST /api/auth/token` has no limit on attempts, like the web login. A user deleted or demoted keeps their token until it expires (no user deletion exists yet). `Monolithic` keeps HTTP Basic. Without `APP_JWT_SECRET` the application starts with a random key (fails open, with a warning); a public deployment with the `demo` profile and no secret would use the public development secret, so it could be made to fail at startup outside local (#122 review).
- **Swagger UI (#111):** the page needs internet in the browser (jsDelivr) and runs that third-party script in the web origin, with SRI and a pinned version but no Content-Security-Policy; the WebJar (option B) or a CSP limited to `/api-docs/**` would harden it. The Docker image could not be built in the session (no daemon): the first Render deploy after #111 must answer `GET /openapi.yaml` with 200, which checks the `.dockerignore` exception.
- **Web frontend (#124, ADR 0016):** htmx 4 (out since 2026-08) is a later decision; still no Content-Security-Policy, although every script now comes from the application's own origin (the Alpine.js standard build needs `'unsafe-eval'` or its CSP build); `lucide-static` adds 11.5 MB to the jar (copying only the sprite would avoid it); Motion is upgraded by hand (`static/vendor/motion/README.md`) until a WebJar exists. htmx requests send the CSRF token as the forms' hidden field (#125), so a future htmx call that is not a form (`hx-get` with a side effect, `hx-delete`) would need the token as a header.
- **htmx on the account detail (#125):** htmx logs a console error for the 4xx answers it receives (the 404 page swapped in, the 401 of an expired session); harmless, but visible in the browser console. The error page swapped into `body` keeps the URL of the detail.
- **htmx navigation (#126):** per-field validation on blur (`hx-trigger="blur"` with a validation endpoint) was left out; it fits a field that needs a server answer while typing (for example, whether a username is taken in the sign-up). Without JavaScript, the back button after a POST asks to resend the form, because pages are `no-store` (unchanged behaviour). An expired session on a boosted navigation answers `HX-Redirect: /login` without saving the request, so after logging in the user lands on `/` instead of the page they were going to; `HtmxLoginRedirect.commence` could save GET requests in the request cache (#126 review).
