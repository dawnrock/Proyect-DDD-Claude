# Loose pending items

> Annex of [`estado-del-proyecto.md`](estado-del-proyecto.md). **It is not read at the start of every session**: look it up when planning an issue (there may be notes for it) and when closing a PR (to add or remove pending items).

- Telegram: notices are on since 2026-10-30. If they had to be silenced again, `TELEGRAM_DISABLED=1` (PR #40) in `~/.claude/settings.json`. The failed-CI notice does not depend on that variable (it uses the GitHub secrets).
- **Event outbox (#165, ADR 0021):** one instance only: the relay reads pending rows without row locks (with several instances, `SELECT … FOR UPDATE SKIP LOCKED`, which also works on H2 2.4 in PostgreSQL mode). Delivery is at least once, so a future real consumer (e-mail, Telegram) must be idempotent. Failed rows (`failed_at`) stay in the table and are only visible in the log (`log.error`) and in the database; there is no screen or retry command for them.
- **Login (#50):** the H2 console (`/h2-console`) is for administrators only (same-origin frames, no CSRF on its forms) and the public `/actuator/health` only gives the status; a user can find out whether an IBAN exists by trying a transfer (risk accepted in ADR 0008); login attempts are limited since #130 (ADR 0017). No password change or user deletion; since #103 customers can sign up (users in the database since #150). An account can be assigned to a user that does not exist yet. On the public Render deployment (#85) the H2 console is off and the password must be strong.
- **PMD baseline (#168, ADR 0020):** design smells that existed when the analysis entered the build; each needs its own refactoring issue (Clean Code course, ch. 19 and 22) and, when done, its line out of `pmd-baseline.properties`: `CheckingAccount` (`GodClass`; `reconstitute`, `CyclomaticComplexity` 15); `validate()` of `OpenAccountCommandDef` and `SignUpCommandDef` (`CyclomaticComplexity` 11). `CheckingAccountService` and its tests left the baseline in #174, `AccountWebController` in #177.
- **Application services split (#174 review):** `AccountOpener.save` returns the view (`AccountSummary`), so it mixes saving with presenting, and `DueSegmentReview.reviewIfDue` both saves and answers whether the holder was demoted (inherited); `UsernameAvailability` is built twice (stateless). The ADRs (0006, 0008, 0012, 0020) and the frozen contracts keep the names of their time (the contracts have a "Since #174" line). The PMD coupling threshold (20) shaped the split: a new collaborator in a service may need another extraction.
- **Web controllers split (#177 review):** `OpenAccountWebController`, `AnotherAccountWebController` and `AccountListController` use constants and helpers of `AccountDetailView` (`CURRENCIES`, `MESSAGE`, `redirectToDetail`, `isCustomer`), so the opening screens depend on the detail's component; a small `WebAttributes` holder would untie them. `AccountDetailView.isCustomer(Caller)` hides a `listAccounts` query behind a view helper (same queries as before #177).
- **Numbers Checkstyle does not see (#167 review):** `MonABankIbans` appends `"142800"` (`ES00` as digits, ISO 13616) as a string literal; the IBAN and NIF lengths live inside regexes (`ES\\d{22}` in `AccountNumber`, `\\d{7}` in `TaxId`, which must change together with `CONTROL_LETTER_POSITION`). Candidates for named constants if a later Clean Code pass wants them; `MagicNumber` only checks numeric literals.
- **Segment review (#98):** `Transaction.occurredOn` uses `Instant.now()` while the review uses the `Clock` bean, so tests move the clock forward instead of dating the movements and there is no end-of-month test; in a transfer only the source account is reviewed; the account detail does not show the date of the next review.
- **Tax agency failures (#98 review):** an exception from `IncomeVerifier` during a segment review aborts the withdrawal or transfer that triggered it, and stops the daily `reviewSegments` for the remaining accounts. The fake agency never fails; decide the behaviour when a real adapter exists.
- **Customer sign-up (#103):** Accepted risks of ADR 0012: no e-mail verification (sign-ups are limited since #131, ADR 0018), a failed user creation after `signUp` would leave a customer without login (the user is created after the use case's transaction, #150). `isUsernameTaken` and the existing-customer checks of the admin opening are not atomic with the save beyond the global lock of the unit of work; since #150 unique constraints on document and username back them. Review of #103: a customer saved without a username (only after a partial failure, which the order of operations avoids) cannot get another account (400) nor sign up again (`DuplicateCustomerException`); the administrator can give a new customer a username that already exists as a Spring Security user (the core does not know them); `CustomerOwnershipRepository.assign` replaces the username of a customer (documented, unused by the use cases).
- **Contract tests (#107, ADR 0013):** Schemathesis runs in the CI with deterministic generation; it still warns that `POST /api/transfers` mostly gets 404 (it invents account ids) and that `signUp` rejects most generated documents (random DNIs rarely have a valid control letter): better test data (demo account ids in `schemathesis.toml`, or an example of a valid document) would let it reach more logic. Adapter-level validation in the `@WebMvcTest`s (`swagger-request-validator`) stays an optional later step with its own ADR. On the web chain an undeclared `QUERY` gets 403 (CSRF), not 405.
- **JWT on the API (#122, ADR 0015):** no revocation or deny list (a stolen token is valid until it expires, 15 min; changing `APP_JWT_SECRET` invalidates all of them), no refresh token, and `POST /api/auth/token` is limited in attempts like the web login since #130 (ADR 0017). A user deleted or demoted keeps their token until it expires (no user deletion exists yet). `Monolithic` keeps HTTP Basic. Without `APP_JWT_SECRET` the application starts with a random key (fails open, with a warning); a public deployment with the `demo` profile and no secret would use the public development secret, so it could be made to fail at startup outside local (#122 review).
- **Contract version rule on Windows (#159):** checked again by Claude on 2026-11-25 with the Windows conditions reproduced on Linux (CRLF working copy, LF base from `git show`): unchanged contract, change without a bump and a patch bump through oasdiff v1.35.0 give the same result as with LF. A run on real Windows (`BASE_REF=Hexagonal node scripts/check-contract-version.mjs`) is optional; no machine of the user was attached to the session. `.gitattributes` still only pins `mvnw` and `*.cmd`: other tools read the contract with CRLF without trouble.
- **Swagger UI (#111):** the page needs internet in the browser (jsDelivr) and runs that third-party script in the web origin, with SRI and a pinned version but no Content-Security-Policy; the WebJar (option B) or a CSP limited to `/api-docs/**` would harden it.
- **Web frontend (#124, ADR 0016):** htmx 4 (out since 2026-08) is a later decision; still no Content-Security-Policy, although every script now comes from the application's own origin (the Alpine.js standard build needs `'unsafe-eval'` or its CSP build); `lucide-static` adds 11.5 MB to the jar (copying only the sprite would avoid it); Motion is upgraded by hand (`static/vendor/motion/README.md`) until a WebJar exists. htmx requests send the CSRF token as the forms' hidden field (#125), so a future htmx call that is not a form (`hx-get` with a side effect, `hx-delete`) would need the token as a header.
- **Accessible field errors (#145 review):** `app.js` refocuses the first `[aria-invalid="true"]` after every `htmx:afterSettle`, not only after a failed submit (harmless today: the panel and the body are replaced whole); the template guard's regex would miss a tag whose Thymeleaf expression contains `>` (the `>= 20` count would warn); `*-error` ids are only prefixed in `detail.html`, so a page with two forms sharing a field name would need prefixes too. The focus has no automated test (no JS harness; a browser test suite would need its own ADR).
- **Show password (#146 review):** without JavaScript the hidden button stays the input group's last child, so the password input's right corners are square (cosmetic); the step-2 test that checks the input → button → error order with a regex is tied to the markup.
- **htmx on the account detail (#125):** htmx logs a console error for the 4xx answers it receives (the 404 page swapped in, the 401 of an expired session); harmless, but visible in the browser console. The error page swapped into `body` keeps the URL of the detail.
- **htmx navigation (#126):** per-field validation on blur (`hx-trigger="blur"` with a validation endpoint) was left out; it fits a field that needs a server answer while typing (for example, whether a username is taken in the sign-up). Without JavaScript, the back button after a POST asks to resend the form, because pages are `no-store` (unchanged behaviour). An expired session on a boosted navigation answers `HX-Redirect: /login` without saving the request, so after logging in the user lands on `/` instead of the page they were going to; `HtmxLoginRedirect.commence` could save GET requests in the request cache (#126 review).
- **Login attempt limit (#130, ADR 0017):**
  - **Cloudflare ranges:** run `node scripts/check-cloudflare-ips.mjs` now and then to keep `app.security.trusted-proxies` in sync (the client IP on Render was checked by the user after #133).
  - **In-memory counters:** they reset on restart and are not shared if the service ever runs several instances.
  - **Shared IPs:** a network behind one IP (NAT) is blocked as a whole after 10 failures.
  - **Clients on internal addresses:** the internal ranges are trusted proxies, so a client that reached the container from one of them could choose the IP that counts. On Render clients only arrive through Cloudflare and Render's proxy (#130 and #133 reviews).
  - **IPv6 clients:** the per-IP counter keys on the full /128 address, so a client with a /64 can rotate addresses to get past `max-per-ip` (the user + IP limit has the same gap). Grouping IPv6 addresses by /64 would close it (#133 review).
- **Sign-up limit (#131, ADR 0018):**
  - **Global cap as a denial of service:** someone with many IPs can fill the 50 sign-ups per hour and stop legitimate sign-ups for up to an hour (accepted: it keeps the memory bounded).
  - **Probing counter without a global cap (#139 review):** failures free their sign-up slot, so they do not use `max-total`; someone with many IPs (rotating IPv6 addresses, for example) can grow the failures map, up to 10 instants per IP for an hour, pruned every 1,000 operations. Each failure needs a taken username or an existing document; a cap on the number of IPs in the map would bound it.
  - **`release` is not tied to its reservation:** it removes the last instant of the IP and of the total, not the one reserved; with a window much shorter than a sign-up it could give back another reservation. Harmless with the 1 h window; `tryReserve` could return the reserved `Instant` (#131 review).
  - **In memory and shared IPs:** same as the login limit (reset on restart, one instance, a NAT shares the quota of 3); the per-IP counter has the same IPv6 /64 gap, bounded by the global cap.
- **Real persistence (#150, ADR 0019):**
  - **Neon live since 2026-11-23:** the `Hexagonal` service runs with `SPRING_PROFILES_ACTIVE=demo,prod` on Neon (database `monabank`); since #156 the `prod` profile sets the connection timeouts. Checked by Claude on 2026-11-25 through Render's API: `SPRING_DATASOURCE_URL` is now the plain URL (`…/monabank?sslmode=require`), and the deploy connected to a cold Neon in about 8 s and started with no error. Flyway `V2` (outbox, #165) was applied on Neon on 2026-11-24. The tests run on H2 in PostgreSQL mode; Testcontainers would add a check on a real PostgreSQL (it needs Docker in the CI).
  - **Tests of the login use an in-memory store (#157):** the `@WebMvcTest`s import `TestUsers` (`InMemoryUserDetailsManager`, case-insensitive), so they cannot catch behaviour that depends on the JDBC store; login rules that depend on it are tested in `CaseInsensitiveLoginTests` and `DddLabApplicationTests`.
  - **Concurrency:** one fair lock around each transaction (one instance). Several instances would need row locks (`PESSIMISTIC_WRITE`, with the deadlock risk of crossed transfers) or optimistic locking carried through the domain: `@Version` on `checking_account` only guards within a transaction, because the aggregate does not carry the version.
  - **Not yet up to date:** `docs/analysis/technical-analysis.md` (Spanish analysis) still describes in-memory persistence. `CLAUDE.md` was updated to JPA/Flyway (H2 locally, Neon in `prod`) with the user's approval on 2026-11-25.
  - **Users vs. customers:** the user is created after the sign-up transaction (`CustomerRegistration`), so a failure between both would leave a customer without login, as before.
  - **Review of #150:** a unique index violation (document, account number) that got past the checks would reach the user as an untranslated `DataIntegrityViolationException`, and a lost update caught by `@Version` as an `OptimisticLockingFailureException` (500); neither can happen with the lock and one instance. The demo loader skips loading as soon as one account exists, so a start that failed halfway through the demo would leave it incomplete for good (each opening is its own unit). `AccountHolder.reconstitute` cannot check the segment against the balance on its own; the account's `reconstitute` checks what depends on both.
