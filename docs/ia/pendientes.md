- Telegram: notices are on since 2026-10-30. If they had to be silenced again, `TELEGRAM_DISABLED=1` (PR #40) in `~/.claude/settings.json`. The failed-CI notice does not depend on that variable (it uses the GitHub secrets).
- **Demo data (#11):** `./mvnw spring-boot:run` starts with the `demo` profile (`spring-boot.run.profiles` property in `pom.xml`) and three accounts opened through the use cases (since #19, by `adapter.in.cli.DomainModelRunner`, which also deposits, withdraws and transfers); `-Dspring-boot.run.profiles=default` starts without data. Suggest to the user mentioning it in the commands section of `CLAUDE.md` (needs their approval).
- **Synchronous event consumers (#17):** `AuditLogListener` and `CustomerNotificationListener` run in the use case's thread: if one failed, the error would reach the user with the account already saved. Accepted while they only write to the log. When a listener that does something real is needed (email, Telegram…), make it asynchronous (`@Async` or `@TransactionalEventListener` with real persistence) so it does not affect the use case. Also, `pullDomainEvents()` empties the list before publishing: if a listener fails, the remaining events are lost (in a transfer, the target's too). A real listener will need an outbox or `@TransactionalEventListener` (#17 review).
- **Team in the cloud (#18):** the teammates were launched as subagents in local worktrees (`feat/account-factory-back` and `-web`, not pushed); they could not talk to each other and the lead merged their contract reviews. The web side's web e2e test failed in its worktree until the back was integrated (expected with a contract that changes account opening).
- **Login (#50):** the H2 console (`/h2-console`) is for administrators only (same-origin frames, no CSRF on its forms) and the public `/actuator/health` only gives the status; a user can find out whether an IBAN exists by trying a transfer (risk accepted in ADR 0008); there is no limit on login attempts. No user management (sign-up, password change): users are static. An account can be assigned to a user that does not exist yet.
- **Team (#50):** the teammates cannot write to each other (no `SendMessage`); the lead merges their contract reviews. The isolated worktrees still start from `Monolithic`: the initial `git merge --ff-only` worked.
- **`implement-plan-team` and isolated worktrees (#7):** the worktree that `Agent` creates with `isolation: worktree` starts from `Monolithic`, not from the integration branch, and is only deleted if the agent finishes without changes. What worked: the teammate first runs `git merge --ff-only <integration-branch>`. A session hook stops the lead from writing in another worktree, so the lead integrates in its own worktree. It should be reflected in the skill (needs the user's approval, because it touches `.claude/`).
- **Notes from the #7 review (still open after phase 2):** save both accounts of a transfer in one transaction (today they are two `save` calls without a lock; documented in the glossary); consider an `approved()` or an `application` enumeration instead of comparing the `"REJECTED"` literal on the web.
- **Latent issue (#6 review):** `CheckingAccount.tryWithdraw` records the transaction before evaluating `isAllowed`; on an account not in EUR, a high net worth customer would trigger `CurrencyMismatchException` (the limit is in EUR) with the `PENDING` transaction already recorded. It does not happen today because no account can be opened in a currency other than EUR (the minimum deposit is in EUR too). Fix it by evaluating before recording when other currencies are allowed.
