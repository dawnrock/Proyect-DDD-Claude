# Plan: Static analysis in the build (Checkstyle, PMD/CPD, SpotBugs)

- **Issue:** [#168](https://github.com/dawnrock/Proyect-DDD-Claude/issues/168)
- **Type:** feature
- **Phase:** 2 · Hexagonal architecture
- **Base branch:** `Hexagonal`
- **Date:** 2026-11-24
- **Status:** in progress
- **Total estimate:** ~80 min (10 tasks)

## Goal

Add the three static analysis tools of the Clean Code course (ch. 25, Lab 3.5) to `./mvnw verify`, so the build and the CI fail when the code breaks the agreed rules: naming conventions and magic numbers (Checkstyle), design smells and duplication (PMD + CPD), and probable bugs (SpotBugs). The course's guidelines apply: few rules, agreed and versioned, the level required of new code, and no warning that everyone learns to ignore.

The analysis run on 2026-11-24 in a scratch copy found 1,080 Checkstyle warnings (#166 and #167 bring them to 0), 9 PMD, 1 CPD and 23 SpotBugs warnings. This plan configures the tools so that the false positives are excluded explicitly, the existing design smells are recorded in a baseline, and the real bugs are fixed.

### Out of scope

- Refactoring `CheckingAccountService`, `AccountWebController`, `CheckingAccount` and the two `validate()` methods (own issues; listed in `pendientes.md`).
- SonarQube as a server or in the CI; Error Prone.
- `Monolithic`, frozen.

**Generated code.** Immutables writes 16 classes to `target/generated-sources/annotations` (`OpenAccountCommand`, `AccountDetails`, `AccountDetailsResponse`…). Checkstyle and PMD only read `src/main/java` and `src/test/java`, so they never see them. SpotBugs reads the bytecode and does. The generated classes carry `@org.immutables.value.Generated` in the bytecode, so the exclusion can match that annotation if SpotBugs' filter supports it (to check in T8). Otherwise, a class-name regex over the 16 generated classes is used: every `*Def` interface in `application` and `adapter.in.rest` gives a class with the same name without `Def`.

**PMD baseline.** `excludeFromFailureFile` (a `.properties` file: `class=Rule1,Rule2`) makes `pmd:check` and `pmd:cpd-check` ignore the listed violations and fail on any other one. The report still shows them, so they stay visible.

**Order (user, 2026-11-24): #166 → #167 → #168 → #165.** #166 and #167 go first: without them Checkstyle would fail with more than a thousand warnings. The event outbox (#165) goes after this plan, so it is written with the three tools already active; it takes ADR 0021.

## Risks and open questions

- **After this plan comes #165** (event outbox). Its new classes (entity, relay, properties) must pass the three tools; its plan already names the defaults as constants and takes ADR 0021.

- **Build time.** The three tools took about 25 s in total in the scratch copy (Checkstyle ~6 s, PMD+CPD ~7 s, SpotBugs ~12 s). T9 measures it on the real build. If it is too much locally, `-Dcheckstyle.skip -Dpmd.skip -Dcpd.skip -Dspotbugs.skip` can be documented for quick runs, never for the CI.
- **SpotBugs filter by annotation.** If the filter cannot match `@org.immutables.value.Generated`, the regex over class names must be updated when a new `*Def` is added. A comment in `spotbugs-exclude.xml` and in `ApplicationValue` will say so.
- **`CLAUDE.md` and `.claude/` changes** need the user's explicit approval (working agreement). They are listed in T10 so they can be reviewed in the PR.
- **Maven 3.10 and `maven.java.net`.** The course adds `-Daether.remoteRepositoryFilter.prefixes=false` to `.mvn/maven.config` to silence a certificate warning from an old repository declared by a Checkstyle dependency. It did not appear in the scratch run (the wrapper's Maven version); add it only if the warning shows up.
