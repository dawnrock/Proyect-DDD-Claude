- **Type:** feature
- **Phase:** 2 · Hexagonal architecture
- **Base branch:** `Hexagonal`
- **Date:** 2026-11-24 (revised the same day: order and adjustments)
- **Status:** in progress
- **Total estimate:** ~90 min (10 tasks)

## Goal

Domain events are published today after the unit of work commits, synchronously, to the `@EventListener`s of `application.listener`. An event is lost if the process stops between the commit and the publication, and a failing consumer turns into an error for the user after the money has moved, losing the events still to publish. This plan stores the events in an **outbox table in the same transaction as the aggregate** and delivers them with a **scheduled relay**, at least once, with retries, so the use case no longer depends on its consumers.

Decisions taken by the user on 2026-11-24 (issue #165): relay only with `@Scheduled` (1A); writer and relay both in `adapter.out.event` (2A); Jackson with a logical type name and an explicit registry (3A2); one instance, documented (4A).

**Order (user, 2026-11-24): after #166, #167 and #168.** The issue is not urgent: the consumers only write to the log. Going after the Clean Code issues means the outbox is written with the new test naming convention (#166) and with Checkstyle, PMD/CPD and SpotBugs already in `./mvnw verify` (#168), and #166 does not conflict with the test files this plan changes. ADR 0020 is taken by #168, so this plan writes **ADR 0021**.

### Out of scope

- A message broker or a real consumer (e-mail, Telegram): the relay delivers to the local `@EventListener`s.
- Several instances (`FOR UPDATE SKIP LOCKED`, which works on PostgreSQL and on H2 2.4): noted in `pendientes.md`.
- Making the listeners idempotent: they only write to the log, so a duplicate is a duplicated log line (documented).
- The domain: it keeps recording events and handing them over with `pullDomainEvents()`.
- `Monolithic`.

Technical decisions inside the user's choices (Claude, reversible):

- **Table** `domain_event_outbox`: `id bigint generated by default as identity` (delivery order), `event_type varchar(100)`, `account_id uuid`, `payload varchar(4000)` (an event is ~300 characters of JSON), `occurred_on`, `recorded_at`, `published_at` (null while pending), `attempts integer default 0`, `failed_at` (null unless it gave up), `last_error varchar(1000)`; index on `published_at`. Same SQL for PostgreSQL and H2, like V1.
- **Serialisation:** Jackson 3 (`tools.jackson`, already in the project) serialises the event records without annotations and reads them back through their canonical constructor (checked on 2026-11-24 with `MoneyDeposited` and `CheckingAccountOpened`). By default it also writes derived `is…()` accessors (`positive`, `negative`, `monABank`), so the adapter's mapper turns off is-getter detection: the payload holds only the record components. Logical name = the event's simple name, registered by hand in `DomainEventTypes`; a test scans `domain.model` with ArchUnit's `ClassFileImporter` and fails if a `DomainEvent` is not registered.
- **Relay:** `fixedDelay` (never overlaps itself), interval `app.events.outbox.relay-interval=2s`, batch `app.events.outbox.batch-size=100`. Each event is delivered and marked on its own (a failure does not roll back the others); after `app.events.outbox.max-attempts=5` failures the row gets `failed_at`, a `log.error` and is no longer retried. The relay method is guarded by a lock, so a direct call (tests) never overlaps the scheduled one. A failing event does not hold back the later ones (the listeners are independent log lines).
- **Named defaults (Clean Code, #167 and #168):** the defaults of `OutboxProperties` are constants (`DEFAULT_RELAY_INTERVAL`, `DEFAULT_BATCH_SIZE = 100`, `DEFAULT_MAX_ATTEMPTS = 5`, `DEFAULT_RETENTION`), applied with `Objects.requireNonNullElse` like `LoginAttemptsProperties`, so Checkstyle's `MagicNumber` and SpotBugs' `BX_UNBOXING_IMMEDIATELY_REBOXED` stay quiet.
- **Clean-up:** `@Scheduled(cron = "0 30 3 * * *")` deletes rows published more than `app.events.outbox.retention=7d` ago; failed rows are kept for inspection.
- **Static analysis (#168):** the new code must pass `./mvnw verify` with Checkstyle, PMD/CPD and SpotBugs. The SpotBugs exclusion of `URF_UNREAD_FIELD` already covers `adapter.out..*Entity`, so `OutboxEventEntity` needs no new exclusion. `CheckingAccountService` is in the PMD baseline (`GodClass`, `CouplingBetweenObjects`); T4 must not add new types to it.
- **Order of the tasks:** the application change (T4) goes before the new publisher (T6), so `./mvnw verify` stays green at every step with the old `SpringDomainEventPublisher` until the relay exists.

## Risks and open questions

- **Depends on #166, #167 and #168 being merged.** If the order changes again, revert the adjustments of the revision: ADR 0020, Spanish `snake_case` test names, and no static-analysis criterion.
- **Delay:** consumers get events up to ~2 s later. Harmless while they only log; a consumer that needs it at once would need publishing right after the commit (option 1B), without changing the table.
- **Duplicates:** if the process stops after delivering an event and before marking it, it is delivered again. Accepted (at least once); future consumers must be idempotent (ADR 0021).
- **Neon:** the relay queries the outbox every 2 s while Render is awake; Neon already stays awake then (health check and keepalive, #156), so no extra compute hours.
- **Transaction size:** the listeners ran inside the transaction only between T4 and T6; after T6 nothing but the outbox insert runs in it.
