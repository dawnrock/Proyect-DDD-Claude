## Goal

Start the application with sample accounts so it can be tried right away (the course's `DomainModelRunner`). An `ApplicationRunner` active only with the `demo` profile opens **3 accounts through the use cases** (`CheckingAccountService.openAccount`), never through the repository, so the demo data obeys the same rules as real data. `./mvnw spring-boot:run` activates `demo` by default; tests and a plain `java -jar` do not.

The issue also asks for a test-data builder with Lombok's `@Builder` in a `support` test package: it replaces the three private "open an account" helpers that the domain and persistence tests duplicate today.

### Out of scope

- Demo movements (deposits, withdrawals, transfers): the runner only opens accounts, as the issue says (see Risks).
- Changes to the REST API or the web: `GET /api/accounts` and the list page already show the accounts. OpenAPI does not change.
- Layered ArchUnit rules (#12).

## Context

- **Where the runner lives:** `application` (as `docs/arquitectura/fase-1-capas.md` lists for #11): it orchestrates use cases, like a scripted client. `com.pronoide.ddd.application.DemoDataLoader`, `@Component @Profile("demo")`, `@RequiredArgsConstructor` + `@Slf4j` (allowed outside the domain). It depends only on `CheckingAccountService` (D3), never on the repository.
- **The 3 accounts:** two retail and one high net worth, all in EUR and above the 50.00 EUR minimum deposit (R1), with valid Spanish IBANs (R14):

  | Account number | Holder | Segment | Initial deposit |
  | -------------- | ------ | ------- | --------------- |
  | `ES9121000418450200051332` | Ada Lovelace | `RETAIL` | 1,000.00 |
  | `ES7921000813610123456789` | Grace Hopper | `HIGH_NET_WORTH` | 5,000.00 |
  | `ES6000491500051234567892` | Alan Turing | `RETAIL` | 250.00 |

  (Final values are chosen in T3; the test checks count, segments and that they come from the service. Some numbers are also used by `DddLabApplicationTests`; there is no clash because the demo profile runs in its own Spring context.)
- **Profile wiring:** `@Profile("demo")` keeps the runner out of every test context (`@SpringBootTest` and `@WebMvcTest`) unless a test activates it. `spring-boot:run` gets the profile from the plugin configuration (`<profiles><profile>demo</profile></profiles>` in `spring-boot-maven-plugin`), which can still be overridden with `-Dspring-boot.run.profiles=…`. No new dependency.
- **Repository is in memory:** the runner runs once per start-up on an empty repository, so it needs no "already loaded" check. If an account number were already in use, `openAccount` would throw `DuplicateAccountNumberException` and the start-up would fail loudly, which is acceptable for demo data.
- **Test builder:** `src/test/java/com/pronoide/ddd/support/TestAccounts.java` with `@Builder(builderMethodName = "anAccount", buildMethodName = "open")` on a static factory method that calls `CheckingAccount.open(...)` (domain tests keep building the aggregate with its factory, as `src/test/CLAUDE.md` asks). Defaults for any field not set (IBAN, holder "Ada Lovelace", `RETAIL`, `100.00` EUR), because `@Builder` on a method has no `@Builder.Default`. Usage: `anAccount().segment(HIGH_NET_WORTH).initialDeposit("500.00").open()`.

## Risks and open questions

- **Accounts only, no movements:** with no movements, the detail pages of the demo accounts are almost empty. Adding a deposit, a rejected withdrawal and a transfer through the use cases would make the demo more useful; it is left out because the issue only asks for accounts.
- **`spring-boot:run` with the profile on by default** also affects anyone who runs the app that way to try something without data; they can override it with `-Dspring-boot.run.profiles=default`.
- **Account numbers already used in `DddLabApplicationTests`** do not clash: the demo profile runs in its own Spring context (`DemoProfileTests`).
