# Plan: Mon-A Bank customer sign-up on Hexagonal

- **Issue:** [#103](https://github.com/dawnrock/Proyect-DDD-Claude/issues/103)
- **Type:** feature
- **Phase:** 2 · Hexagonal architecture
- **Base branch:** `Hexagonal`
- **Date:** 2026-11-15
- **Status:** in progress
- **Total estimate:** ~280 min (30 tasks; back and web in parallel after T0)
- **Twin of:** #95, implemented on `Monolithic` in PR #102 (branch `feat/customer-sign-up`). Both branches must behave the same.

## Goal

Bring the Mon-A Bank customer sign-up of #95 to the hexagonal architecture: `/login` with two doors and a three-step sign-up that leaves the customer signed in; `POST /api/customers` (public); customers identified by their document (DNI or NIE with control letter) who can hold several accounts ("Abrir otra cuenta" on the web, the administrator by document); every IBAN generated by the bank and replaceable only by another generated one (`POST /api/accounts/{id}/account-number`). Users are created at runtime in the input adapter (ADR 0012).

### Out of scope

- Same as #95: e-mail verification, password recovery, rate limiting, persisting users, "Abrir otra cuenta" through REST.
- New domain events for sign-up or IBAN changes (see open questions).
- Changing `Monolithic`.

## Context

What `Hexagonal` already has: `TaxId` (8 digits + letter, no control letter, no NIE, `toUpperCase()` without locale), the output port `AccountNumberSequence` with `InMemoryAccountNumberSequence` (same 9999/0001 algorithm), `CheckingAccountFactory` (IBAN + segment by verified income), input ports `CheckingAccountCommands` / `CheckingAccountQueries`, `UnitOfWork`, domain events and `AccountOwnershipRepository` (application port, account → username). The administrator's opening already has no `accountNumber` and requires `holderName`, `holderTaxId` and `ownerUsername`.

What is missing: customers, e-mail, public sign-up, runtime users, another account, IBAN regeneration and every screen of #95.

Decisions taken in this plan (behaviour fixed by #95; design adapted to ports):

- **Rules:** on `Hexagonal` the free numbers start at R28. Mapping with `Monolithic`: R28 ↔ R27 (DNI/NIE with control letter), R29 ↔ R28 (e-mail), R30 ↔ R29 (one customer per document and one customer per username), R31 ↔ R30 (bank IBAN), R32 ↔ R31 (IBAN replaced only by another generated one, admin only).
- **`Customer` aggregate** in `domain.model` with `TaxId` and `EmailAddress`, and the output port `CustomerRepository` (`save`, `findByTaxId`; R30 atomic in the adapter) implemented by `adapter.out.persistence.InMemoryCustomerRepository`.
- **Customer ↔ username** is identity, not domain: an application port `CustomerOwnershipRepository` (like `AccountOwnershipRepository`): `assign(TaxId, username)` rejecting a username that belongs to another customer, `usernameOf(TaxId)`, `customerOf(username)`. Adapter in `adapter.out.persistence`.
- **Factory:** `CheckingAccountFactory.open(Customer, MonetaryAmount)` opens an account for a customer (holder copies name and document; segment by verified income). The current `open(holderName, taxId, deposit)` stays only if something still needs it.
- **IBAN replacement:** `CheckingAccount.reassignAccountNumber(AccountNumber)` (R32) with `AccountNumber.isMonABank()`; the repository adapter reindexes the number.
- **Input ports:** `CheckingAccountCommands` gains `signUp`, `openAnotherAccount`, `regenerateAccountNumber`; `CheckingAccountQueries` gains `isUsernameTaken`. Every command runs in the `UnitOfWork`, so sign-up and opening are all or nothing.
- **Runtime users:** `CustomerRegistration` in `adapter.in` (root, shared support like `SecuritySupport`), synchronized, as on `Monolithic` (username free in users and customers → `signUp` → create the `USER`).
- **Web and REST:** port the screens, forms, controllers and tests of PR #102 from `presentation.web` / `presentation.rest` to `adapter.in.web` / `adapter.in.rest` (same routes, messages and behaviour).
- **Admin opening:** `OpenAccountCommand` gains `holderEmail`; `holderName`, `holderEmail` and `ownerUsername` become optional (required for a new customer; for an existing one blank or equal, otherwise 400). Details view gains `holderTaxId` and `holderEmail` (default `""`).
- **ADR 0012** (same number as on `Monolithic`; ADR 0011 only applies to phase 1). `TaxId` keeps `Locale.ROOT` as on `Monolithic` (#99 review).
- **Team plan:** `/implement-plan-team 103`. Teammates in isolated worktrees (`isolation: worktree`, then `git merge --ff-only <contract commit>`): a session hook blocks writing into other worktrees.

## Risks and open questions

- **Where the customer ↔ username relation lives:** decided by the user on 2026-11-15: application port `CustomerOwnershipRepository`.
- **Domain events:** decided by the user on 2026-11-15: no new events (`CustomerRegistered`, `AccountNumberReassigned` stay out).
- **PR #102:** merged on 2026-11-15; the web port copies its merged code (`origin/Monolithic`).
- **Incompatible REST change** in `POST /api/accounts` (optional customer fields, new `holderEmail`).
- Accepted risks of ADR 0012 and the review notes of #95 (customer saved before the account, reassign before the uniqueness check) apply as well; with the unit of work they may already be covered.
