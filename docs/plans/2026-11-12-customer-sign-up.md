- **Issue:** [#95](https://github.com/dawnrock/Proyect-DDD-Claude/issues/95)
- **Type:** feature
- **Phase:** 1 · Layered monolith
- **Base branch:** `Monolithic` (frozen; `src/` exception authorised by the user on 2026-11-12; the `v1-monolito` tag does not move)
- **Date:** 2026-11-13 (revision 3: customer with several accounts, built on #99, names shared with `Hexagonal`; open questions answered by the user the same day)

- **Total estimate:** ~275 min (29 tasks; back and web in parallel after T0)

## Goal

A visitor can become a customer of **Mon-A Bank** without the administrator. `/login` shows two doors ("Ya soy cliente" / "Quiero ser cliente"); the second one opens a three-step sign-up (personal data, access, account) that registers the customer, creates the user and opens the account at once, and leaves the customer signed in on the account detail. A customer is identified by their document: they can hold several accounts, but cannot sign up twice. Every IBAN is generated by the bank, and the administrator can only replace one with another generated IBAN.

### Out of scope

- E-mail verification, password recovery or change, rate limiting of sign-ups.
- Opening another account through the REST API as a customer: web only (decided by the user on 2026-11-13).
- Adding up the balances of a customer's accounts: the segment is still decided per account (R20-R26).
- Validating the check digits of IBANs typed by the user (transfer targets).
- Persisting users and customers: they live in memory, like the accounts.
- The same change on `Hexagonal`: twin issue, created after this one is merged (there `TaxId` and the generated IBAN already exist).

## Context

Decisions confirmed by the user (2026-11-12 and 2026-11-13):

- **Bank:** Mon-A Bank. IBAN generated with entity `9999` and branch `0001`, always assigned by the bank; the administrator can only replace it with another generated one.
- **Screens:** `/login` with two doors and a three-step sign-up (data, access, account), as in the mock-ups (https://claude.ai/artifact/A4rJn3LtCGA8LMTLexE9J9, C for the entry + B for the sign-up).
- **Customer with document and e-mail.** The document is unique per **customer**, not per account: the public sign-up rejects an existing document ("ya eres cliente"); a signed-in customer can "Abrir otra cuenta" giving only the deposit; the administrator can open another one for an existing customer by giving their document.
- **Immediate opening**, without administrator approval. The segment is not asked (decided by verified income and balance, #99).
- **REST** in the style of the OpenAPI: `POST /api/customers` (public) and `POST /api/accounts/{id}/account-number` (administrator).
- **Reuse `Hexagonal`'s names** (`TaxId`, `AccountNumberSequence`) and coordinate with #99. On `Monolithic` the free rule numbers start at R24; #99 takes R24-R26, so this plan uses **R27-R31**.
- **Answers to the open questions (2026-11-13):** (1) the administrator's opening for an existing customer **rejects** a name, e-mail or username that differs from the customer's (400); (2) "Abrir otra cuenta" is **web only**; (3) `TaxId` is **extended to NIE with the control letter checked**, and the twin issue does the same on `Hexagonal`.

Decisions taken in this plan:

- **Order with #99: #99 first, not merged.** #99 adds `TaxId` to the holder and asks the agency at opening; this plan builds on it and only adds what is specific to customers. One PR each keeps the domain rule apart from a large back + web team feature.
- **The document is `TaxId`**, the value object #99 copies from `Hexagonal`; no `IdentityDocument`. The issue asks for DNI and NIE with their control letter, so T1 extends `TaxId`: DNI (8 digits + letter) or NIE (`X`/`Y`/`Z` + 7 digits + letter), control letter checked (R27). The three demo tax ids (`12345678Z`, `87654321X`, `11111111H`) already have valid letters. The twin issue carries the same extension to `Hexagonal` (confirmed by the user). The shared pattern `OpenAccountCommandDef.TAX_ID_PATTERN` (used by the command, the REST request and the web form since #99) accepts NIE too.
- **`Customer` aggregate** (new, `domain.model`): `id`, `TaxId taxId`, `fullName`, `EmailAddress email`; created with `Customer.register(...)`. It does not know users (the domain knows nobody). `EmailAddress` is a new value object (R28). `AccountHolder` stays as on `Hexagonal` (name, tax id, segment); each account copies the customer's name and tax id into its holder, and the e-mail is read from the customer.
- **One customer per document (R29):** checked by the use cases against `InMemoryCustomerRepository` (`persistence`), with `DuplicateCustomerException` (domain, 422 "Ya eres cliente de Mon-A Bank…"). The repository keeps the customer → username relation outside the aggregate, like `InMemoryAccountOwnershipRepository` does for accounts (`save(customer, username)`, `findByTaxId`, `findByUsername`).
- **Account numbers (R30):** `InMemoryAccountNumberSequence` in `persistence`, a concrete class with `AccountNumber next()` (no `AccountNumberSequence` interface: ADR 0004). Same algorithm as `Hexagonal`'s adapter: `ES` + IBAN check digits (mod 97) + `9999` + `0001` + Spanish control digits + sequential 10-digit number from `0000000001`. Deterministic: the demo accounts always get the same IBANs. `9999` is invented.
- **IBAN replacement (R31):** `CheckingAccount.reassignAccountNumber(AccountNumber)` accepts only a Mon-A Bank number (`AccountNumber.isMonABank()`) different from the current one. The service takes it from the sequence; nobody types it.
- **Administrator opening:** the command loses `accountNumber`. It carries `holderTaxId` and the deposit; `holderName`, `holderEmail` and `ownerUsername` are required only when the document is not a customer yet. If the customer exists, those fields must be blank or match the customer (otherwise `IllegalArgumentException`, 400), and the account is opened for that customer and their username.
- **Users at runtime.** `application` must not depend on Spring Security (ArchUnit), so credentials stay in `presentation`: a shared `CustomerRegistration` component checks that the username is free, calls `CheckingAccountService.signUp` and then creates the user (`USER`, BCrypt) in the `InMemoryUserDetailsManager`. If the use case fails, no user is created.
- **Wizard state:** a session-scoped `SignUpForm` (`@SessionAttributes`), one validation group per step, cleared on completion. The password stays in the server session between steps 2 and 3, never in the page.
- **Routes.** Web: `GET /login` (doors), `GET /login?form` (form; `?error` also shows it), `GET|POST /signup`, `/signup/access`, `/signup/account`, `GET|POST /accounts/another` (customers), `POST /accounts/{id}/account-number` (administrators). REST: `POST /api/customers` (public, `201` + `Location: /api/accounts/{id}`) and `POST /api/accounts/{id}/account-number` (administrator, `200` with the account summary).
- **Incompatible REST change:** `POST /api/accounts` loses `accountNumber`; `holderName`, `holderEmail` and `ownerUsername` become conditional.
- **New ADR 0012** (customer self sign-up) extending ADR 0008 (ADR 0011 is taken by #99's `integration` layer).
- **Team plan:** back and web in parallel after the contract (`/implement-plan-team 95`). Existing types (`OpenAccountCommandDef`, `AccountDetailsDef`, REST request, admin form) change only in the integration task T20, so both sides compile against the frozen contract.

## Risks and open questions

- **`TaxId` with NIE and control letter** goes beyond what `Hexagonal` validates today: until the twin issue is done, the two branches accept different documents.
- **Segment per account:** a customer's second account asks the agency again and decides its own segment; balances are not added up (existing behaviour).
- **Sign-in after sign-up (T17):** depends on how Spring Security 7 stores a programmatic authentication in the session. Fallback: redirect to `/login?form` with a "ya puedes entrar" notice.
- **Atomicity:** customer, account and user are created in steps; if creating the user failed afterwards, a customer without a usable login would remain. Accepted for an in-memory practice project and noted in the ADR.
- **Public endpoint without limits:** anybody can create customers; on Render the data disappears on restart. Accepted risk, recorded in ADR 0012.
- **Incompatible REST change** in `POST /api/accounts` and many tests with fixed IBANs to rewrite (T20 is the largest task).
- **Password in the session** between steps 2 and 3: never rendered, cleared on completion or session expiry.
- **Entity code `9999`:** invented; changing it touches one constant and its tests.
