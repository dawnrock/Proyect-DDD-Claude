- **Issue:** [#198](https://github.com/dawnrock/Proyect-DDD-Claude/issues/198)

- **Base branch:** `Hexagonal`
- **Date:** 2026-11-26

## Goal

Option (b) of the first entry, as in a real bank: someone who signed up in Auth0 and is not a monA Bank customer yet completes the sign-up in the app (name, document, e-mail, a username and the first account) **without a local password**. The bank stops handling the passwords of new customers. The customer, their account, a local user with role `USER` and an unusable password, and the `external_identity` link are created together; then the web goes back to Auth0 (silent, as after linking in #196) and the customer lands on their account, signed in with Auth0.

Third of four issues: #196 (done) → #197 (done) → **#198** → #199 realistic mode in production.

### Out of scope

- Turning the classic sign-up (with password) off when `app.auth.local=false`, and the REST sign-up `POST /api/customers` in that mode (#199). Here the classic sign-up stays exactly as it is.
- Signing up through the API with an Auth0 token: the REST sign-up does not change (no contract change).
- A customer number generated by the bank instead of a username chosen by the customer.

## Context

**Entry.** An unknown Auth0 identity already lands on `/login/link` with a `PendingIdentity` in the session (#196). That page becomes a choice: «¿Ya eres cliente? Vincula tu usuario» (today's form) **or** «¿Aún no eres cliente? Date de alta» → `GET /signup?auth0`, which starts the same three-step wizard in **Auth0 mode** (`SignUpForm.externalIdentity = true`), with the e-mail prefilled from Auth0 (editable). The pending identity must be present and not expired on every step; otherwise → `/login?link-expired`.

**Wizard in Auth0 mode** (same controller, same form, same rules: ADR 0012, the #103 rule, the validations of #181):

| Step | Classic | Auth0 mode |
| ---- | ------- | ---------- |
| 1 · Personal data | as today | as today, e-mail prefilled |
| 2 · Access | username + password twice | **only the username** (new validation group `ExternalAccess`); the text says the customer will sign in with Auth0 |
| 3 · Account | as today | as today; on success → `redirect:/oauth2/authorization/auth0` instead of the programmatic sign-in |

**Registration.** `CustomerRegistration` (root of `adapter.in`) gets `registerWithExternalIdentity(SignUpCommand, PendingIdentity, clientIp)`, sharing everything with `register`: the sign-up limit (ADR 0018, slot given back on failure, probing counter), the username checks, the use case `AccountOpeningCommands.signUp`. Differences: the pending identity must not be expired (checked first, nothing created), the user gets an **unusable password** (BCrypt of 32 random bytes nobody knows: no form login, no `POST /api/auth/token`), and `ExternalIdentities.link(provider, subject, username)` runs right after creating the user. `application` does not change (the use case already receives no password).

**No programmatic sign-in.** As in #196, the session is only created by Spring Security's OAuth2 flow: after the sign-up, the controller removes the pending identity and redirects to `/oauth2/authorization/auth0`; Auth0 still has its session, the round trip is silent, and `LinkedOidcUserService` now finds the link. The welcome flash message would not survive the external round trip, so the account page is the confirmation (its IBAN is on it).

**Team issue** (`equipo`): back = `CustomerRegistration` and its tests; web = link page, wizard mode, step 2, templates. Contract first (`docs/contracts/auth0-sign-up.md`).

| Layer / package | File | Change |
| --------------- | ---- | ------ |
| `adapter.in` (support) | `CustomerRegistration` | `registerWithExternalIdentity(...)`, unusable password, link |
| `adapter.in.web` | `SignUpController`, `SignUpForm`, `IdentityLinkController` | Auth0 mode, `ExternalAccess` group, success → Auth0 |

## Risks and open questions

- **The username is still chosen by the customer** (step 2 keeps it, without password): it is the key of ownership and the name in the header. A bank-generated customer number would be more realistic but changes ownership, the header and the API; left out.
- **Partial failure:** the user and the link are created after the use case's transaction (as in today's sign-up, #150), so a failure between them would leave a customer without login or without link. The order (checks → use case → user → link) and the early checks keep it unlikely; noted in `pendientes.md`.
- **No welcome message** after the Auth0 round trip (a flash attribute does not survive it); the account page shows the IBAN.
- **Not tried against a real tenant** until it is deployed; the manual check goes in `render.md`.
